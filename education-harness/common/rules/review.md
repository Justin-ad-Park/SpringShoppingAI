# 강사 관점의 검토 기준

## 교육 검토

1. 학습 목표를 새 API 이름 없이 설명할 수 있는가?
2. 필요한 선수 지식을 먼저 배웠는가? 새 문법과 새 기술을 한꺼번에 도입하지 않는가?
3. 예제의 입력·처리·결과가 명확한가? 기능이 필요한 적절한 사례인가?
4. 설명 → 그림 → 코드 → 실행 결과가 실제 같은 동작을 설명하는가?
5. 초급자가 직접 읽을 핵심과 제공되는 보조 코드를 구분했는가?
6. 한 번에 읽을 범위와 예상 시간이 현실적인가? 다운로드·API 대기·오류 해결 시간과 구분했는가?
7. 같은 설명의 반복, 불필요한 제작 이력, 모호하거나 어색한 표현이 있는가?
8. 보충 문서의 권장 시점, 진입·복귀 링크와 확인 질문이 적절한가?
9. 비교 실험에 수정 전 결과, 재시작·재적재 여부, 원복 안내와 실제 관찰 경로가 있는가? 준비된 입력·데이터가 비교하려는 차이를 만들 수 있는가?
10. 확인 질문이 현재 페이지의 자료를 대상으로 하는가? 문서 분리 후에도 ‘위·아래·앞서’의 대상이 존재하는가? 소수업·단원·전체 시간과 주차 계획이 맞는가?

11. 제목·목표·도입·예제·확인 질문이 같은 학습 내용을 다루는가? 목표가 예제 이름·내부 API 나열이나 하지 않는 일로 대체되지 않았는가? 부모 목차의 완료 기준도 일치하는가?
12. 각 설명은 지금 이해할 내용에 필요한가? 예제 세부 조건·오류 처리·운영 한계가 기본 흐름보다 앞서지 않는가? 삭제할 문장과 뒤로 옮길 문장을 구분했는가?
13. 설명을 줄이면서 현재 예제의 계산 근거·비용·실패 후 상태·검증 한계까지 없애지 않았는가? ‘미사용 기능 나열 삭제’를 모든 범위 설명 삭제로 확대하지 않았는가?

## 기술 검토

1. 실제 기술 버전과 API 서명·설정 경로가 맞는가?
2. 설명의 호출 시점·메시지·판단 주체·실행 주체가 코드와 일치하는가?
3. 전체 코드라고 표시한 예제가 실제 파일과 일치하는가? 발췌·설명용 코드는 생략 범위가 명확한가?
4. 단원·하위 문서·실행 모듈 번호가 대응 정보와 맞는가? 파일 이동 후 링크·명령이 유효한가?
5. 로컬 검증과 실제 외부 서비스 검증을 구분했는가? 실행하지 않은 테스트가 통과했다고 쓰이지 않았는가?
6. 프로젝트 전체 테스트 명령이 의도하지 않은 외부 호출을 포함하지 않는가?
7. 설정에 개인 경로·실제 키·필요 없는 환경 의존성이 들어 있지 않은가?
8. 다이어그램의 처리·분기·호출 순서가 코드의 실제 동작 또는 명시한 가능한 경로와 일치하는가?
9. ‘이 문장의 근거가 제시된 코드 어디에 있는가?’ 객체 생성·요청 구성·실행·결과 읽기와 클래스 이름·설정 차이를 확인할 수 있는가? 생략했다면 실제 소스로 연결했는가?
10. 직접 구현과 라이브러리 기능을 대응시킬 때 저장·변경 시점, 실패 후 상태, 예외 처리 범위의 차이를 확인했는가? 오류 코드 설명이 실제 처리 범위를 넘지 않는가?
11. 성공·검증 상태가 보장하는 범위와 확인하지 않는 범위가 명확한가? 부분 검사 통과를 요청 전체 처리 완료로 설명하지 않는가?

## 결과 형식

| 중요도 | 위치 | 확인한 문제 | 학습자가 혼동할 이유 | 개선안 |
|---|---|---|---|---|
| 높음·중간·낮음 | 파일과 절 또는 줄 | 구체적인 문장·코드·구조 | 어떤 오해나 실패로 이어지는가 | 최소한의 수정 방향 |

- 높음: 실행 차단, 사실 오류, 핵심 개념의 오해, 필수 선수 지식 누락.
- 중간: 순서·설명량·중복·예제 문맥 때문에 이해가 어려움.
- 낮음: 표현·편집·표기 일관성 개선.
- 단순한 선호 차이를 오류로 판정하지 않습니다. 좋은 기존 구성도 짧게 기록합니다.
- 검토만 요청받으면 파일을 수정하지 않습니다. 직접 확인한 사실과 추정·미확인을 구분합니다.
- 변경이 필요 없는 검토를 억지로 만들어 내지 않습니다.
