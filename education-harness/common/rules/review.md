# 강사 관점의 검토 기준

요청·변경 유형에 해당하는 묶음과 질문만 선택합니다. 해당하지 않는 항목마다 별도 답변을 작성하지 않습니다.
상세 작성 방법은 [작성 규칙](authoring.md)을 참조합니다. 각 질문은 하나의 판단을 중심으로 확인합니다.

## 교육 검토

### 목표와 설명 흐름 — 목표·본문·수업 구조를 검토할 때

- 목표가 학습자가 설명하거나 수행할 수 있는 행동을 나타내는가?
- 제목·도입·예제·확인 질문이 같은 학습 목표를 다루는가?
- 질문이 샘플 고유의 이름·코드 위치 찾기로 끝나지 않고 해당 수업의 원리·사용법을 확인하는가? 프레임워크 기능과 샘플 정책을 구분하는가?
- 설명 순서가 학습 목표에 맞는가? 정상 동작 또는 실패·복구 중 수업의 중심이 분명한가?
- 가정하지 않은 선수 지식은 필요한 위치에서 설명하는가?
- 한 번에 읽는 범위가 주요 학습 내용을 이해하고 확인하기에 적절한가?
- 학습 목표와 관계없는 제작 이력·미사용 기능 설명이 본문을 가리지 않는가?
- 설명을 줄이면서 필요한 계산 근거·비용·실패 후 상태·검증 한계를 없애지 않았는가?

### 예제·과제·문서 연결 — 해당 자료를 제공하거나 바꿀 때

- 예제의 입력·처리·결과가 명확한가?
- 그림·코드·실행 결과가 같은 동작을 설명하는가?
- 직접 읽을 핵심 코드와 제공되는 보조 코드가 구분되는가?
- 수행 과제의 대상·방법·확인할 결과가 명확한가?
- 코드 변경 과제·비교 실험에 변경 전후 비교와 필요한 재시작·재적재·복원 안내가 있는가?
- 준비된 입력·데이터로 비교하려는 차이를 확인할 수 있는가?
- 실패 사례가 학습 목표나 사용법 이해에 필요한가?
- 보충 문서의 진입·복귀 경로와 권장 학습 시점이 명확한가?
- 확인 질문과 ‘위·아래·앞서’의 대상이 현재 페이지에 존재하거나 실제 링크로 연결되는가?
- 질문의 대상 설정·코드·수치가 이름과 값·단위로 명확하고, 판단에 필요한 발췌가 질문 가까이에 있는가?
- 해설의 조건·적용 범위·API 반환 대상이 질문과 일치하며, 샘플 수치를 일반적인 보장으로 설명하지 않았는가?
- 확인 질문은 같은 제목 아래 모였으며, 모든 답이 하나의 기본 접힘 해설에 있고 여러 질문의 번호와 답 번호가 대응하는가?

## 기술 검토

### 사실·소스·경로 — 설명·코드·파일 위치를 바꿀 때

- 기술 버전과 API 서명·설정 이름이 실제 사용 버전과 맞는가?
- 호출 시점과 판단·실행 주체의 설명을 코드에서 확인할 수 있는가?
- 전체 소스·발췌·설명용 예제의 표시가 실제 제공 범위와 맞는가?
- 다이어그램의 처리·분기가 실제 구현 또는 명시한 가능한 경로와 맞는가?
- 단원·실습의 대응과 변경 후 링크·명령이 유효한가?

### 설정 — 연결·환경·실행 설정을 바꿀 때

- 공유 설정의 기준 위치가 명확한가?
- 테스트의 별도 설정은 검증 조건·환경 분리에 필요한가?
- 중복 제거를 위해 독립 예제 사이에 불필요한 설정 의존성을 추가하지 않았는가?
- 같은 동작에 영향을 주는 설정의 적용 범위·우선순위를 확인했는가?
- 설정 변경이 의도한 동작에 반영되는지 확인했는가?
- 개인 경로·실제 키·불필요한 환경 의존성을 넣지 않았는가?

### 상태·오류 — 처리 결과나 실패 동작을 다룰 때

- 상태 이름이 실제 통과한 검사의 범위와 일치하는가?
- 작업을 정상 수행한 빈 결과와 필요한 작업을 수행하지 않은 경우를 구분하는가?
- 빈 목록·0원의 의미를 해당 업무의 성공 조건으로 판단하는가?
- 일반 실패 응답으로 바꾼 예외의 처리 위치·오류 종류를 확인할 수 있는가?
- 진단 정보에 인증 정보나 불필요한 민감 원문을 기록하지 않는가?
- 오류 코드 설명이 실제 예외 처리 범위와 맞는가?

### 테스트와 검증 근거 — 테스트·실행 안내·완료 기록을 바꿀 때

- 테스트 이름으로 조건과 기대 동작을 알 수 있는가?
- 테스트 종류와 실제 외부 호출 여부가 구분되는가?
- 검증 명령이 의도한 테스트를 선택하는가?
- 전체 테스트에 의도하지 않은 외부 호출이 포함되지 않는가?
- 독립 업무 규칙은 적절한 수준의 테스트에서 확인하는가?
- 단순 위임·구현 반복만 확인하는 불필요한 테스트가 없는가?
- 결과 출력이 학습에 필요한 값을 보여주면서 assertion을 유지하는가?
- 단계 주석은 이해에 도움이 되는 곳에만 쓰이고 실제 처리 단계와 맞는가?
- 실행한 검증과 미검증 범위를 구분하는가?
- 로컬 연결·값 검증 통과를 실제 외부 연결이나 모델 품질의 근거로 확대하지 않는가?

### 이름·책임·리팩터링 — 이름이나 구조를 바꿀 때

- 이름만으로 동작·역할과 대상을 파악할 수 있는가?
- 이름이 실제 상태·완성도를 오해하게 하지 않는가?
- 같은 역할의 용어와 언어·인터페이스 계약을 지키는가?
- 책임 분리가 핵심 흐름의 이해를 돕는가?
- 형식을 맞추기 위한 불필요한 타입·계층을 추가하지 않았는가?
- 호출부와 현재 문서가 바뀐 구조에 맞는가?
- 리팩터링 후 초기화·순서·상태·실패의 기존 계약이 유지되는가?
- 구현을 라이브러리 기능으로 바꾸면 저장·실패 정책의 차이를 확인했는가?
- 오류 수정은 의도한 동작 변경과 회귀 검증을 명시하는가?
- 코드 형식과 결과 예시가 프로젝트 관례 및 실제 코드에 맞는가?

## 결과 형식

중요도·위치·확인한 문제·이유·최소 개선안을 표나 목록으로 제공합니다. 여러 항목이면 적용 순서를 안내합니다.

- 높음: 실행 차단, 사실 오류, 핵심 개념의 오해, 필수 선수 지식 누락.
- 중간: 순서·설명량·중복·예제 문맥 때문에 이해가 어려움.
- 낮음: 표현·편집·표기 일관성 개선.
- 단순한 선호 차이를 오류로 판정하지 않습니다. 좋은 기존 구성도 짧게 기록합니다.
- 검토만 요청받으면 파일을 수정하지 않습니다. 직접 확인한 사실과 추정·미확인을 구분합니다.
- 변경이 필요 없는 검토를 억지로 만들어 내지 않습니다.
