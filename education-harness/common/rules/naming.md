# 역할을 드러내는 이름

이 문서는 교육 코드의 변수·상수·메서드·타입·패키지 이름에 관한 기준 위치입니다. 작성 규칙·검토 절차·템플릿은 이 기준을 연결하며 상세 규칙을 복사하지 않습니다. 대상 언어와 과정의 고유한 패키지 구성은 프로젝트 설정에서 정합니다.

## 문맥 안에서 뜻을 읽을 수 있게 짓기

- 변수·타입은 담은 값과 역할을, 메서드는 수행하는 동작과 대상을 드러냅니다. 선언뿐 아니라 호출하는 문장에서도 뜻이 이어지는지 읽습니다. `run`, `data`, `value`, `result`, `handle`처럼 여러 뜻이 가능한 이름은 주변 타입·메서드만으로 의미가 충분한지 먼저 판단합니다. 짧거나 널리 쓰인다는 이유만으로 일괄 변경하지 않습니다.
- 이름만으로 역할을 구분하기 어렵다면 `chatClient`, `requestMessages`, `policyVectorStore`처럼 필요한 대상을 붙입니다. 클래스·패키지에서 이미 충분히 설명하는 프로젝트 이름이나 같은 수식어를 반복해서 붙이지 않습니다. 반복문의 짧은 인덱스, 좁은 람다의 `product`처럼 문맥이 분명한 이름도 유지합니다.
- 이름을 설명하기 위해 주석에 다른 의미를 덧붙여야 한다면 이름부터 고칩니다. 주석은 정책·단위·제약·선택 이유를 보충합니다. `stopped`에 중단 원인을 담는 대신 `stopReason`으로 표현하는 식입니다.
- 같은 역할에는 같은 단어를 씁니다. 서로 다른 역할은 구분합니다. 예를 들어 요청 메시지와 응답 메시지, 모델이 고른 후보와 Java가 검증한 결과, 검색한 정책과 실제 인용한 정책을 한 이름으로 부르지 않습니다. 독립 실습 사이의 이름 통일을 위해 공통 실행 모듈을 만들지는 않습니다.

## 동작·타입·상태의 의미

- 메서드는 조회·생성·변환·검증·실행·출력을 구분합니다. 예를 들어 `createConversationKey`, `parseToolResult`, `verifyCitations`, `executeTool`처럼 무엇을 처리하는지 읽히게 합니다. `create`, `get`, `set`, `print`는 예시이며 언어와 기존 API의 관례를 우선합니다. 프롬프트 상수는 `SYSTEM`보다 `CRITERIA_EXTRACTION_INSTRUCTION`처럼 목적을 표시합니다.
- 타입은 객체가 가진 책임이나 전달하는 자료를 나타냅니다. `Selection`, `Draft`, `Source`만으로 선택 대상·검증 전후·검색 자료를 구분하기 어렵다면 `CandidateEvidenceSelection`, `UnverifiedAnswer`, `PolicySearchResult`처럼 구체화합니다. 상태 이름이 실제 검사보다 넓은 성공이나 완성도를 암시하지 않게 합니다.
- 클래스의 동작과 이름·설명을 맞춥니다. `Executor`는 작업 실행, `Workflow`는 처리 순서 조정처럼 실제 책임으로 판단합니다. `@Service`라는 애너테이션만을 이유로 모든 클래스에 `Service`를 붙이지 않으며, 명확한 `ProductCatalog` 같은 도메인 이름은 유지합니다.
- 닫힌 종류·단계·중단 원인을 여러 곳에서 문자열로 주고받아 오타나 값 추적을 어렵게 한다면 Enum을 검토합니다. 설명은 값별 의미와 전이를 짧게 보충합니다. 외부 프로토콜의 문자열이나 단일 위치의 단순 값까지 일괄 Enum으로 바꾸지 않습니다.
- 수량·제한은 세는 대상과 증가 시점을 드러냅니다. `clients`, `maxModels` 대신 실제 의미에 맞는 `clientCreations`, `modelRequestAttempts`, `maxModelRequestAttempts`를 씁니다. 성공 뒤 증가하는 완료 수와 요청 전 증가하는 시도 수를 구분합니다. 시간은 단위와 기준을 표시합니다. `timeoutMs`는 허용 기간, `deadlineNanos`는 마감 시각이며 서로 바꿔 부르지 않습니다.

## 이름 변경이 계약을 바꾸지 않게 하기

- 이름을 고르기 전에 선언 → 대입·증가 → 분기·비교 → 반환·직렬화 → 호출부까지 추적합니다. 자료형이 같아도 역할이 다른 값을 구분하고, 변경 후 같은 경로를 다시 대조합니다.
- 인터페이스 메서드·외부 API·언어가 생성하는 접근자 이름은 지킵니다. 도구 이름과 도구 매개변수명도 모델에 제공되는 JSON 스키마의 일부일 수 있습니다. Java 지역변수를 바꾸듯 전역 치환하지 않습니다.
- HTTP 경로·요청 매개변수·JSON 필드·설정 키·도구 입력·출력 등 외부 계약은 내부 이름과 구분합니다. 내부 이름만 개선할 때는 기존 외부 이름을 유지하고, 계약 변경이 필요하면 호출부·고정 응답·테스트·교재까지 함께 변경해 그 차이를 명시합니다.
- 사용처·정적 import·메서드 참조·코드 예제·현재 문서 링크를 함께 수정합니다. 과거 검증 기록에 남은 당시 이름은 이력으로 보존합니다. 불필요한 구 이름의 별칭은 만들지 않습니다.

## 패키지 이름과 배치

- 패키지는 파일 수나 Spring 빈 여부가 아니라 책임과 의존 방향으로 정합니다. 업무 규칙, 모델·검색 연동, 요청 흐름, 도구 노출, 실행 보조 기능을 구분할 필요가 있는지 판단합니다. 구체적인 패키지명과 예시는 프로젝트 설정을 따릅니다.
- 업무 데이터·조건·계산·업무 검증은 프레임워크 연동과 구분합니다. Spring 빈이 아니라는 이유만으로 전송 DTO·검색 결과·실행 기록을 모두 도메인 객체로 분류하지 않습니다.
- 작은 예제의 읽기 흐름이 이미 분명하면 기존 위치를 유지합니다. 같은 역할이 모이거나 서로 다른 책임이 섞여 이해를 방해할 때 하위 패키지를 만듭니다. 모든 실습에 동일한 패키지 세트·계층·인터페이스를 강제하지 않습니다.

## 변경 전후 확인 순서

1. 실제 역할과 기존 외부 계약을 소스·호출부에서 확인합니다.
2. 지금 이름으로 오해할 수 있는 값을 한 문장으로 설명하고, 필요한 이름만 수정합니다.
3. 클래스 이름·설명·필드·메서드·호출 문장이 같은 의미인지 대조합니다.
4. 사용처·교재·테스트를 맞추고, 영향을 받는 동작을 검증합니다. 정적 검색 통과를 모델 판단 품질이나 실제 외부 연결 성공으로 표현하지 않습니다.
