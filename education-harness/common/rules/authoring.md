# 교육 문서와 샘플 코드 작성 원칙

## 설명 수준과 순서

- 대상 독자와 선수 지식은 프로젝트 설정을 기준으로 합니다. 해당 기술의 전문 용어를 이미 안다고 가정하지 않습니다.
- 한 소수업에서는 주요 새 개념 하나를 다룹니다. 문제 → 개념 → 필요한 그림 → 코드 → 실행 → 결과 해석으로 연결합니다.
- 새 문법과 프레임워크 기능을 구분합니다. 필요한 문법은 먼저 짧게 설명합니다.
- 처음 보는 기능을 설명하기 위해 아직 배우지 않은 기능을 선행 의존성으로 사용하지 않습니다.
- 설명을 나눌 때는 코드의 실행 가능성을 유지합니다. 장황한 추상화나 공통 프레임워크로 학습 코드를 감추지 않습니다.
- 전체 소스·일부 발췌·구조 설명용 예시를 구분합니다. 생략한 생성·설정 코드가 있으면 어디에서 준비되는지 안내합니다.
- 다른 모델·도구·서버가 등장하면 누가 판단하고 누가 실행하며 무엇이 전송되는지 설명합니다.

## 설명의 근거와 동작 범위

- 설명하는 동작은 제시한 코드에서 확인할 수 있어야 합니다. 생성자만으로 요청별 재사용을 설명하는 것처럼 근거가 생략되어 있다면 필요한 필드·메서드를 함께 보여주거나 실제 소스로 연결합니다.
- 객체 생성, 요청 구성, 실제 외부 호출, 결과 읽기를 구분합니다. 메서드 이름만으로 실행 시점을 추정하지 않고 사용 버전의 구현·공식 근거를 확인합니다.
- 직접 구현을 라이브러리 기능으로 바꿀 때는 정상 결과뿐 아니라 저장·변경 시점, 실패 뒤 남는 상태, 예외 처리 범위가 같은지도 비교합니다. 동작이 달라지면 차이를 설명합니다.
- 성공·검증 완료 같은 상태 이름에는 통과한 검사와 확인하지 않은 범위를 명시합니다. 형식·ID·값 검사 통과를 요청 전체 처리 완료나 내용의 정확성 보장으로 확대하지 않습니다.

## 실행 가능한 예제

- 구현 수업은 동작하는 코드, 필요한 설정, 실행 위치, 명령, 기대 결과와 테스트를 함께 제공합니다.
- 개념 수업은 실행 코드가 없어도 됩니다. 실행을 제공하지 않은 예제를 완성된 실습이라고 표현하지 않습니다.
- 기본 예제는 가장 단순한 정상 흐름을 보여줍니다. 이후 입력이나 옵션 하나를 바꾸고 결과를 비교합니다.
- 비교 실험은 수정 전 결과 확보 → 하나 변경 → 필요시 재시작·재적재 → 같은 입력으로 비교 → 원복 순서로 안내합니다. 무엇을 어디에서 확인할지 응답 필드·로그·테스트 검증문 등 실제 경로를 제시합니다.
- 실험 데이터로 기대한 차이를 확인할 수 있는지 검사합니다. 현재 출력에 없는 횟수나 내부 입력을 응답 문장만으로 추정하게 하지 않습니다.
- 오류 처리는 핵심 동작을 이해한 다음 설명합니다. 보조 서버·동시성·추적 코드가 필수 선수 지식이 되지 않게 합니다.
- 모델의 자연어 응답을 고정 문자열과 비교하지 않습니다. 고정 응답 서버의 연결 검증과 실제 모델 품질 평가를 구분합니다.
- 테스트는 실제로 확인하려는 동작을 검증합니다. 구현을 그대로 되풀이하는 테스트나 사소한 문장 수정용 테스트를 만들지 않습니다.
- 코드와 문서의 버전·설정 이름·실행 경로를 대조합니다. 버전 확인 위치는 프로젝트 설정을 따릅니다.

## 쉬운 표현과 문서 분리

- 전문 용어는 쉬운 설명과 함께 소개합니다. 학습자가 할 행동을 구체적으로 씁니다.
- ‘각 행을 읽고 관찰’처럼 학습 범위나 행동이 모호한 표현을 피합니다.
- ‘작은 구현’이라고만 쓰지 말고 어떤 입력을 받아 무엇을 출력하는 실행 코드인지 밝힙니다.
- 긴 내부 동작과 심화 설명은 하위 보충 문서로 나눕니다. 본문 링크·권장 학습 시점·돌아가기 링크를 제공합니다.
- 기본 예제를 먼저, 도구 호출·복수 시스템·예외 등 복잡한 예제를 나중에 배치합니다.
- 교육 계획에는 대상·순서·목표·완료 기준을, 상세 수업에는 예제·프롬프트·실습 절차를 둡니다.
- 학습자 문서에 제작 회의, 개편 근거, 검토 과정이나 내부 승인 이력을 넣지 않습니다.
- 같은 설명을 반복하기보다 기준 문서를 정하고 연결합니다. 여러 문서를 따로 읽어도 필요한 최소 문맥은 제공합니다.
- 확인 질문은 해당 페이지의 코드·표·그림과 연결합니다. 문서 분리 후에도 ‘위·아래·앞서’가 가리키는 대상이 현재 페이지에 있는지 확인하고, 다른 페이지라면 실제 링크로 안내합니다.
- 예상 시간은 읽기·실습 등 포함 범위를 밝힙니다. 소수업·단원·전체 시간과 주차 계획을 함께 맞춥니다.

원칙은 이 파일이 기준이고, 검토 시에는 [검토 질문](review.md)을 적용합니다. 템플릿·절차에는 필요한 작성 칸과 수행 단계만 둡니다.

## 변경과 완료

- 사용자가 조정한 순서·예제·표현을 보존합니다. 수정 요청 범위를 넘어 일괄 재작성하지 않습니다.
- 파일 이동이나 이름 변경 시 본문·보충 문서·실습·빌드 등록·명령·링크를 함께 확인합니다.
- 외부 자료는 정확성과 버전의 근거로 활용하고, 학습 흐름은 자체 교재로 설명합니다. 제공 업체의 규격과 프레임워크 공통 API를 구분합니다.
- 확인하지 않은 것을 일반적인 보장처럼 쓰지 않습니다. 현재 구현의 사실과 학습용 단순화를 구분합니다.
- 완료 기록에는 실행한 검사·결과·미검증 범위를 남깁니다. ‘실패·스킵 없음’ 대신 통과 수와 실패·건너뜀 수를 명확히 씁니다.
- 사용자의 계획·검토·수정 요청을 구분하며, 추가 승인 절차를 임의로 만들지 않습니다.
- 커밋은 프로젝트 설정의 언어·형식을 따릅니다. 제목만으로 끝내지 않고 본문에 주요 변경·검증 결과·미검증 범위를 요약합니다. 실행하지 않은 검증을 통과로 쓰지 않습니다.
