# 교육 문서와 샘플 코드 작성 원칙

## 설명 수준과 순서

- 대상 독자와 선수 지식은 프로젝트 설정을 기준으로 합니다. 해당 기술의 전문 용어를 이미 안다고 가정하지 않습니다.
- 한 소수업에서는 주요 새 개념 하나를 다룹니다. 문제 → 개념 → 필요한 그림 → 코드 → 실행 → 결과 해석으로 연결합니다.
- 새 문법과 프레임워크 기능을 구분합니다. 필요한 문법은 먼저 짧게 설명합니다.
- 처음 보는 기능을 설명하기 위해 아직 배우지 않은 기능을 선행 의존성으로 사용하지 않습니다.
- 설명을 나눌 때는 코드의 실행 가능성을 유지합니다. 장황한 추상화나 공통 프레임워크로 학습 코드를 감추지 않습니다.
- 전체 소스·일부 발췌·구조 설명용 예시를 구분합니다. 생략한 생성·설정 코드가 있으면 어디에서 준비되는지 안내합니다.
- 다른 모델·도구·서버가 등장하면 누가 판단하고 누가 실행하며 무엇이 전송되는지 설명합니다.

## 목표에 맞는 설명과 배치

- 수업에서 해결할 문제와 학습자가 이해하거나 할 수 있게 될 행동을 먼저 정하고, 예제는 그 목표를 지원하도록 선택합니다. 기존 코드에 맞춰 목표를 역으로 정하거나, 코드·클래스의 위치 찾기, 타입·변수·내부 메서드 나열, “무엇을 하지 않는다”는 구분으로 목표를 대신하지 않습니다.
- 제목 → 목표 → 도입 → 예제 → 확인 질문이 같은 개념을 다루는지 대조합니다. 목표에 필요하지 않은 코드가 이해를 방해하면 목표를 넓히거나 설명을 늘리기 전에 예제 축소·단계 분리·선택 확장을 검토합니다. 소수업 목표를 바꾸면 부모 목차의 완료 기준도 맞추고, 교육 계획의 해당 설명과 충돌하는지 확인합니다.
- 각 문장이 이번 목표·현재 예제·실행 결과의 이해에 어떤 도움을 주는지 확인합니다. 필요하지 않은 제작 설명과 미사용 기능 목록은 삭제하고, 뒤에서 필요한 설명은 실제로 사용하는 위치로 옮깁니다.
- 예제의 입력 조건·계산 정책·조건 누락 같은 세부 규칙은 해당 필드를 사용하거나 검증하는 부분에서 설명합니다. 설명 순서는 학습 목표에 맞춥니다. 정상 동작을 처음 배우는 수업에서는 기본 흐름을 먼저 설명하고, 실패·복구가 주제인 수업에서는 필요한 정상 동작을 짧게 복습한 뒤 실패 사례를 중심으로 구성합니다. 목표에 필요하지 않은 동시성·확장 설계는 뒤 소수업이나 선택 보충으로 배치합니다. 나눠 보여주는 코드는 전체·발췌·구조 예시를 구분하고 완전한 실행 소스와 테스트로 연결합니다.
- 단순히 짧게 만들기 위해 필요한 근거를 지우지 않습니다. 현재 목표에 필요한 계산 조건, 실행 비용, 실패 후 상태, 검증 범위의 한계는 해당 동작 옆에 유지합니다. 문장의 삭제·이동 여부는 특정 단어가 아니라 수업 목표와의 관계로 판단합니다.

## 설명의 근거와 동작 범위

- 설명하는 동작은 제시한 코드에서 확인할 수 있어야 합니다. 생성자만으로 요청별 재사용을 설명하는 것처럼 근거가 생략되어 있다면 필요한 필드·메서드를 함께 보여주거나 실제 소스로 연결합니다.
- 객체 생성, 요청 구성, 실제 외부 호출, 결과 읽기를 구분합니다. 메서드 이름만으로 실행 시점을 추정하지 않고 사용 버전의 구현·공식 근거를 확인합니다.
- 직접 제어 코드를 만들기 전에 사용 버전의 기본 제공 기능과 설정을 확인합니다. 직접 구현을 라이브러리 기능으로 바꿀 때는 정상 결과뿐 아니라 저장·변경 시점, 실패 뒤 남는 상태, 예외 처리 범위가 같은지도 비교합니다. 동작이 달라지면 차이를 설명합니다.
- 성공·검증 완료 같은 상태 이름에는 통과한 검사와 확인하지 않은 범위를 명시합니다. 결과 상태는 반환값뿐 아니라 필요한 작업의 수행 여부를 근거로 정합니다. 예를 들어 검색을 정상 수행했으나 조건에 맞는 항목이 없는 경우와 필요한 검색·계산을 수행하지 않은 경우를 구분합니다. 빈 목록이나 0원의 의미는 해당 업무의 성공 조건에 따라 판단합니다. 형식·ID·값 검사 통과를 요청 전체 처리 완료나 내용의 정확성 보장으로 확대하지 않습니다.
- 예상하지 못한 예외를 일반적인 실패 응답으로 바꿀 때는 원인 파악에 필요한 정보를 보존합니다. 기존 예외 전달·로그·관측 수단 중 예제에 적합한 방법을 사용하며, 처리 위치와 오류 종류를 확인할 수 있게 합니다. 인증 정보와 진단에 불필요한 요청·응답 원문은 기록하지 않습니다.

## 설정과 실행 환경

- 같은 실행 범위에서 공유하는 설정은 기준 위치를 정하고 중복 선언을 줄입니다. 테스트에는 검증 조건을 만들거나 실행 환경을 분리하는 데 필요한 설정을 둡니다. 독립 실행하는 예제 사이에는 중복 제거만을 목적으로 공통 설정 의존성을 추가하지 않습니다.
- 같은 동작에 영향을 주는 설정이 여러 위치에 있으면 사용 버전의 적용 범위와 우선순위를 확인합니다. 설정을 변경할 때는 의도한 값이 실제 동작에 반영되는지 관련 테스트나 실행 결과로 확인합니다. 확인을 위해 비밀 설정을 출력하지 않습니다.

## 실행 가능한 예제

- 구현 수업은 동작하는 코드, 필요한 설정, 실행 위치, 명령, 기대 결과와 테스트를 함께 제공합니다.
- 개념 수업은 실행 코드가 없어도 됩니다. 실행을 제공하지 않은 예제를 완성된 실습이라고 표현하지 않습니다.
- 기본 예제는 가장 단순한 정상 흐름을 보여주며 선택 심화 기능 없이 독립 실행되어야 합니다. 확장은 변경 규모와 학습 순서에 따라 같은 코드의 설정 변경·추가 테스트·별도 예제 중 적절한 방식으로 제공합니다. 모듈 분리를 일괄 요구하지 않습니다.
- 학습 목표를 직접 확인하는 데 도움이 되는 경우 작은 수행 과제를 제공합니다. 변경하거나 판단할 대상, 수행 방법, 확인할 결과를 명시합니다. 개념 수업에는 설명·분류·예측 과제를 사용할 수 있으며 모든 단원에 코드 수정 과제를 의무화하지 않습니다.
- 코드 변경 과제와 비교 실험은 수정 전 결과 확보 → 하나 변경 → 필요시 재시작·재적재 → 같은 입력으로 비교 → 원복 순서로 안내합니다. 무엇을 어디에서 확인할지 응답 필드·로그·테스트 검증문 등 실제 경로를 제시합니다.
- 실험 데이터로 기대한 차이를 확인할 수 있는지 검사합니다. 현재 출력에 없는 횟수나 내부 입력을 응답 문장만으로 추정하게 하지 않습니다.
- 실패 처리 자체가 학습 목표이거나 정상 동작만으로는 사용법을 오해할 수 있는 경우에 실패 사례를 보여줍니다. 그 외에는 실패 사례를 생략할 수 있습니다. 보조 서버·동시성·추적 코드가 필수 선수 지식이 되지 않게 합니다.
- 모델의 자연어 응답을 고정 문자열과 비교하지 않습니다. 고정 응답 서버의 연결 검증과 실제 모델 품질 평가를 구분합니다. 로컬 테스트 통과는 확인한 연결·분기·값의 근거로만 기록하며 실제 외부 연결 성공이나 모델 품질까지 확대하지 않습니다.
- 테스트는 실제로 확인하려는 동작을 검증합니다. 구현을 그대로 되풀이하는 테스트나 사소한 문장 수정용 테스트를 만들지 않습니다.
- 코드와 문서의 버전·설정 이름·실행 경로를 대조합니다. 버전 확인 위치는 프로젝트 설정을 따릅니다.

## 읽기 쉬운 이름과 코드 표현

변수·상수·타입·메서드·패키지의 이름은 [역할을 드러내는 이름](naming.md)을 기준으로 작성·검토합니다. 역할·측정값·상태·외부 계약을 확인하는 상세 절차와 예시는 그 문서에서만 관리합니다.

- 코드의 줄바꿈·들여쓰기·주석 형식은 대상 언어와 프로젝트 관례를 따릅니다. 표현을 정리할 때 호출 순서·인자·문자열·동작을 바꾸지 않습니다.
- 코드만으로 결과 구조를 떠올리기 어렵다면 생성 코드 가까이에 들여쓴 결과 예시를 둡니다. 전체·발췌·설명용 구조를 구분하고, 동적 값과 생략 범위를 밝힙니다. 단순한 메서드마다 큰 예시를 의무화하지 않습니다.

## 교육용 객체 설계와 SOLID 적용 수준

- SOLID는 책임과 변경 이유를 찾는 기준으로 사용합니다. 원칙의 형식이나 메서드 수만으로 설계를 판단하지 않습니다.
- 서로 다른 책임·상태 정책이 섞여 이해를 방해할 때 분리합니다. 실제 교체 필요나 검증상의 이점이 없는 인터페이스·상속·범용 계층을 추가하지 않습니다. 공개 진입점의 편의성과 내부 구현 책임은 구분합니다.
- 학습자가 핵심 흐름을 따라가기 쉬워지는지가 최종 판단 기준입니다. 여러 보조 클래스나 미래 단원의 개념을 필수 선수 지식으로 만들지 않습니다.

## 동작을 보존하는 리팩터링

- 이름·표현 정리, 책임 분리, 기능 변경을 구분합니다. 리팩터링에서는 기존 입력·출력·오류·상태 변화의 계약을 먼저 확인하고, 별도 요청 없는 기능·버전·실행 설정 변경을 섞지 않습니다. 오류 수정은 의도적으로 바뀌는 동작과 이를 확인하는 회귀 검증을 명시합니다.
- 가능한 한 학습 코드의 사용법을 유지합니다. 이름 변경이 필요하거나 요청되었다면 호출부·정적 import·메서드 참조·실행 예제·현재 안내를 함께 수정합니다. 과거 검증 기록의 당시 이름은 이력으로 구분합니다. 불필요한 구 API 별칭을 남겨 같은 기능의 이름을 늘리지 않습니다.
- 상태의 소유자를 옮기거나 동시성 처리를 바꿀 때도 기존 초기화·실행 순서·실패 후 상태의 보장을 유지합니다.
- 변경된 경계의 기존 동작 테스트부터 실행하고, 공통 API나 상태 관리가 바뀌면 영향을 받는 사용처까지 검증합니다. 구현 구조를 되풀이하는 테스트 대신 의미 있는 회귀 사례를 보강합니다. 출력과 assertion, 실제 외부 호출의 구분도 유지합니다.

## 학습용 테스트

- 테스트 클래스는 객체 기능의 단위 테스트, 로컬 대체 서버·모델을 사용하는 통합 테스트, 실제 외부 서비스의 Live 테스트를 이름으로 구분합니다. 구체적인 접미사와 선택 명령은 프로젝트 설정에 둡니다.
- 하나의 객체 기능을 Spring·웹 서버·외부 모델 없이 검사할 수 있다면 대상 객체별 단위 테스트로 분리합니다. HTTP 요청을 쓰지 않는다는 이유만으로 모델 어댑터·Advisor·도구 연결 검증까지 단위 테스트로 옮기지 않습니다. 기존 입력·정상·실패 검증과 결과 출력을 보존합니다.
- 대상 객체가 단순 위임만 하고 규칙은 다른 객체의 단위 테스트, 프레임워크 연결은 통합 테스트로 확인된다면 중복 단위 테스트를 강제하지 않습니다. 독립적인 인자 변환·분기·검증·상태 변경이 생기면 그 동작을 기준으로 테스트를 분리합니다.
- 테스트 분리·이름 변경 후 파일명·클래스명·문서 링크·선택 명령을 함께 맞추고, 로컬 실행 명령에 객체 단위 테스트와 모델 통합 테스트가 모두 포함되는지 확인합니다. 이름 구분을 위해 태그·추가 빌드 태스크를 의무화하지 않습니다.
- 준비·실행·검증의 구분이 학습에 도움이 될 때만 Given·When·Then 주석을 사용합니다. 주석은 실제 단계와 맞추며, 형식을 위해 준비 코드나 보조 메서드를 늘리지 않습니다.
- 테스트 메서드명은 프로젝트의 학습자 언어로 읽기 쉽게 작성해, 이름만으로 조건과 기대 동작을 알 수 있게 합니다.
- 학습에 필요한 실제 응답·상태·검증 대상 값을 출력하되, 출력이 assertion을 대신하지 않게 합니다. 출력 형식과 공통 지원 도구의 사용 방식은 프로젝트 설정을 따릅니다.
- 키·인증 헤더·비밀 설정을 출력하지 않습니다. 큰 벡터·문서의 일부만 출력하면 전체 길이와 생략 범위를 표시합니다.
- 외부 모델 연결을 검증하는 방법과 실제 호출 여부를 안내합니다. 로컬·Live 테스트의 제공 단위와 공유 여부는 학습 목표와 프로젝트 정책으로 정합니다. 실제 연결을 검증하지 않았다면 그 사실을 명시합니다. 아직 배우지 않은 기능에 의존하는 예제를 만들지 않습니다.
- 실제 모델의 문구·도구 순서·요청 횟수를 고정 응답과 같다고 가정하지 않습니다. Live는 의미 있는 결과와 구조를 검증하며, 품질 평가 수업은 사례별 판정과 연결 실패를 구분합니다.
- 테스트 실행 명령에는 외부 서비스 호출 여부를 안내합니다. 대상 선택 방식은 프로젝트 설정을 따릅니다.
- 여러 실습에 반복되는 Mock 통신·프로토콜 포장·출력은 테스트 전용 공통 도구로 분리합니다. 학습 대상인 응답 값·시나리오 분기·검증은 단원에 남기고, 운영 코드와 Live의 연결에는 Mock 의존성을 추가하지 않습니다.

## 쉬운 표현과 문서 분리

- 전문 용어는 쉬운 설명과 함께 소개합니다. 학습자가 할 행동을 구체적으로 씁니다.
- ‘각 행을 읽고 관찰’처럼 학습 범위나 행동이 모호한 표현을 피합니다.
- ‘작은 구현’이라고만 쓰지 말고 어떤 입력을 받아 무엇을 출력하는 실행 코드인지 밝힙니다.
- 긴 내부 동작과 심화 설명은 하위 보충 문서로 나눕니다. 본문 링크·권장 학습 시점·돌아가기 링크를 제공합니다.
- 기본 예제를 먼저, 도구 호출·복수 시스템·예외 등 복잡한 예제를 나중에 배치합니다.
- 교육 계획에는 대상·순서·목표·완료 기준을, 상세 수업에는 예제·프롬프트·실습 절차를 둡니다.
- 학습자 문서에 제작 회의, 개편 근거, 검토 과정이나 내부 승인 이력을 넣지 않습니다.
- 같은 설명을 반복하기보다 기준 문서를 정하고 연결합니다. 여러 문서를 따로 읽어도 필요한 최소 문맥은 제공합니다.
- 확인 질문은 해당 페이지의 코드·표·그림과 연결합니다. 문서 분리 후에도 ‘위·아래·앞서’가 가리키는 대상이 현재 페이지에 있는지 확인하고, 다른 페이지라면 실제 링크로 안내합니다.

## 확인 질문과 해설

- 수업에서 배운 작동 원리·판단 근거·사용법·결과 해석을 묻습니다. 샘플 고유의 클래스명·메서드명·상태 문자열·코드 위치를 찾거나 외우는 것만으로 답이 끝나는 질문은 피합니다. 구체적인 코드와 설정은 원리를 설명하는 근거로 사용할 수 있습니다.
- 프레임워크가 제공하는 API·설정·메타데이터와 샘플에서 정한 업무 정책·응답 형식을 구분합니다. 샘플 정책을 묻는다면 이름 자체보다 그 정책을 둔 이유와 변경 시 결과를 묻습니다.
- 실습 준비·언어 문법·테스트 읽기가 명시한 목표인 보충은 해당 목표를 확인하는 질문을 사용할 수 있습니다. 모든 질문을 프레임워크 API 암기로 통일하지 않습니다.
- 수업의 이해를 확인하는 질문 절은 `## 확인 질문`으로 통일합니다. `여기서 멈춰 확인하기` 같은 별도 제목이나 답 없는 질문 절을 중복해서 두지 않습니다. 기존 질문이 여러 절에 흩어졌다면 하나로 모으고 해설을 보완합니다.
- 질문 바로 아래에 모든 답을 하나의 `<details>`로 모으고 `<summary>해설</summary>`을 사용합니다. `open` 속성 없이 기본으로 접어 둡니다. 질문마다 별도 접기 영역을 만들지 않습니다.
- 질문이 여러 개면 질문과 답 모두 번호 목록으로 작성하고, 각 답을 같은 번호의 질문에 대응시킵니다. 질문이 하나면 번호를 생략할 수 있습니다. 완료 기준이나 참고 링크는 답과 구분합니다.
- 해설은 결론 → 적용 대상과 범위 → 이유 순으로 답합니다. 샘플 실행 횟수나 상태값은 개념 설명에 필요할 때 근거와 함께 덧붙이며, 이를 일반적인 보장으로 설명하지 않습니다. 질문에서 특정한 API 반환값·설정·계층을 해설에서도 유지합니다.
- 횟수·시간을 묻는다면 무엇을 세거나 측정하는지와 누적 범위를 밝힙니다. 정확한 수치를 결정하는 도구 루프·재시도·종료 조건 등 필요한 전제를 질문 가까이에 제시합니다. 사용자 요청·프레임워크 호출·모델 HTTP 요청·도구 실행 횟수를 같은 것으로 취급하지 않습니다.
- 질문에서 특정 설정·코드·수치·상태를 판단하게 한다면 그 대상을 이름과 값·단위로 명시하고, 필요한 설정이나 코드 발췌를 질문 바로 앞에 보여줍니다. “이 설정”, “2회”처럼 대상이나 범위가 여러 가지로 해석될 표현만으로 묻지 않습니다.
- 질문을 제공한다면 이 페이지의 내용으로 확인할 수 있는 답을 함께 제공합니다. 목차·실행 안내·선택 참고 문서에 이 형식을 맞추기 위한 질문을 새로 만들지는 않습니다. 본문 중간의 설명용 의문문이나 실행 지시는 확인 질문 절과 구분합니다.

원칙은 이 파일이 기준이고, 검토 시에는 [검토 질문](review.md)을 적용합니다. 템플릿·절차에는 필요한 작성 칸과 수행 단계만 둡니다.

## 변경과 완료

- 사용자가 조정한 순서·예제·표현을 보존합니다. 수정 요청 범위를 넘어 일괄 재작성하지 않습니다.
- 파일 이동이나 이름 변경 시 본문·보충 문서·실습·빌드 등록·명령·링크를 함께 확인합니다.
- 외부 자료는 정확성과 버전의 근거로 활용하고, 학습 흐름은 자체 교재로 설명합니다. 제공 업체의 규격과 프레임워크 공통 API를 구분합니다.
- 확인하지 않은 것을 일반적인 보장처럼 쓰지 않습니다. 현재 구현의 사실과 학습용 단순화를 구분합니다.
- 완료 근거의 작성 여부와 형식은 [검증 절차](../workflows/verify-materials.md#6-완료-근거)를 따릅니다.
- 사용자의 계획·검토·수정 요청을 구분하며, 추가 승인 절차를 임의로 만들지 않습니다.
- 커밋은 프로젝트 설정의 언어·형식을 따릅니다. 제목만으로 끝내지 않고 본문에 주요 변경·검증 결과·미검증 범위를 요약합니다. 실행하지 않은 검증을 통과로 쓰지 않습니다.
