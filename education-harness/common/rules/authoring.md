# 교육 문서와 샘플 코드 작성 원칙

## 설명 수준과 순서

- 대상 독자와 선수 지식은 프로젝트 설정을 기준으로 합니다. 해당 기술의 전문 용어를 이미 안다고 가정하지 않습니다.
- 한 소수업에서는 주요 새 개념 하나를 다룹니다. 문제 → 개념 → 필요한 그림 → 코드 → 실행 → 결과 해석으로 연결합니다.
- 새 문법과 프레임워크 기능을 구분합니다. 필요한 문법은 먼저 짧게 설명합니다.
- 처음 보는 기능을 설명하기 위해 아직 배우지 않은 기능을 선행 의존성으로 사용하지 않습니다.
- 설명을 나눌 때는 코드의 실행 가능성을 유지합니다. 장황한 추상화나 공통 프레임워크로 학습 코드를 감추지 않습니다.
- 전체 소스·일부 발췌·구조 설명용 예시를 구분합니다. 생략한 생성·설정 코드가 있으면 어디에서 준비되는지 안내합니다.
- 다른 모델·도구·서버가 등장하면 누가 판단하고 누가 실행하며 무엇이 전송되는지 설명합니다.

## 목표에 맞는 설명과 배치

- 목표는 학습자가 이해하거나 할 수 있게 될 행동으로 씁니다. 예제 타입·변수 이름, 내부 메서드 나열, “무엇을 하지 않는다”는 구분을 목표 대신 사용하지 않습니다.
- 제목 → 목표 → 도입 → 예제 → 확인 질문이 같은 개념을 다루는지 대조합니다. 소수업 목표를 바꾸면 부모 목차의 완료 기준도 맞추고, 교육 계획의 해당 설명과 충돌하는지 확인합니다.
- 각 문장이 이번 목표·현재 예제·실행 결과의 이해에 어떤 도움을 주는지 확인합니다. 필요하지 않은 제작 설명과 미사용 기능 목록은 삭제하고, 뒤에서 필요한 설명은 실제로 사용하는 위치로 옮깁니다.
- 예제의 입력 조건·계산 정책·조건 누락 같은 세부 규칙은 해당 필드를 사용하거나 검증하는 부분에서 설명합니다. 먼저 정상 변환·호출 흐름을 보여주고 오류 처리·동시성·확장 설계는 뒤 소수업이나 선택 보충으로 배치합니다. 나눠 보여주는 코드는 전체·발췌·구조 예시를 구분하고 완전한 실행 소스와 테스트로 연결합니다.
- 단순히 짧게 만들기 위해 필요한 근거를 지우지 않습니다. 현재 목표에 필요한 계산 조건, 실행 비용, 실패 후 상태, 검증 범위의 한계는 해당 동작 옆에 유지합니다. 문장의 삭제·이동 여부는 특정 단어가 아니라 수업 목표와의 관계로 판단합니다.

## 설명의 근거와 동작 범위

- 설명하는 동작은 제시한 코드에서 확인할 수 있어야 합니다. 생성자만으로 요청별 재사용을 설명하는 것처럼 근거가 생략되어 있다면 필요한 필드·메서드를 함께 보여주거나 실제 소스로 연결합니다.
- 객체 생성, 요청 구성, 실제 외부 호출, 결과 읽기를 구분합니다. 메서드 이름만으로 실행 시점을 추정하지 않고 사용 버전의 구현·공식 근거를 확인합니다.
- 직접 구현을 라이브러리 기능으로 바꿀 때는 정상 결과뿐 아니라 저장·변경 시점, 실패 뒤 남는 상태, 예외 처리 범위가 같은지도 비교합니다. 동작이 달라지면 차이를 설명합니다.
- 성공·검증 완료 같은 상태 이름에는 통과한 검사와 확인하지 않은 범위를 명시합니다. 형식·ID·값 검사 통과를 요청 전체 처리 완료나 내용의 정확성 보장으로 확대하지 않습니다.

## 실행 가능한 예제

- 구현 수업은 동작하는 코드, 필요한 설정, 실행 위치, 명령, 기대 결과와 테스트를 함께 제공합니다.
- 개념 수업은 실행 코드가 없어도 됩니다. 실행을 제공하지 않은 예제를 완성된 실습이라고 표현하지 않습니다.
- 기본 예제는 가장 단순한 정상 흐름을 보여줍니다. 이후 입력이나 옵션 하나를 바꾸고 결과를 비교합니다.
- 비교 실험은 수정 전 결과 확보 → 하나 변경 → 필요시 재시작·재적재 → 같은 입력으로 비교 → 원복 순서로 안내합니다. 무엇을 어디에서 확인할지 응답 필드·로그·테스트 검증문 등 실제 경로를 제시합니다.
- 실험 데이터로 기대한 차이를 확인할 수 있는지 검사합니다. 현재 출력에 없는 횟수나 내부 입력을 응답 문장만으로 추정하게 하지 않습니다.
- 오류 처리는 핵심 동작을 이해한 다음 설명합니다. 보조 서버·동시성·추적 코드가 필수 선수 지식이 되지 않게 합니다.
- 모델의 자연어 응답을 고정 문자열과 비교하지 않습니다. 고정 응답 서버의 연결 검증과 실제 모델 품질 평가를 구분합니다.
- 테스트는 실제로 확인하려는 동작을 검증합니다. 구현을 그대로 되풀이하는 테스트나 사소한 문장 수정용 테스트를 만들지 않습니다.
- 코드와 문서의 버전·설정 이름·실행 경로를 대조합니다. 버전 확인 위치는 프로젝트 설정을 따릅니다.

## 읽기 쉬운 이름과 코드 표현

- 메서드 이름은 동작과 대상을, 변수·타입 이름은 담은 값이나 맡은 역할을 드러냅니다. `handle`, `resolve`, `data`, `scenario`처럼 문맥 없이 역할을 알기 어려운 이름은 구체화합니다. 실제 값을 만드는지, 설정하는지, 조회하는지, 출력·전송하는지도 구분합니다.
- 같은 역할에는 같은 단어를 씁니다. 예를 들어 생성은 `create…`, 설정은 `set…`, 조회는 `get…`, 출력은 `print…`로 구분할 수 있습니다. 이 접두사는 예시이며 대상 언어·프로젝트 관례를 우선합니다. 이름이 짧다는 이유만으로 널리 쓰이는 이름을 일괄 변경하지 않습니다.
- 여러 상황에 재사용하는 설정·콜백은 특정 예제의 결과 대신 기능과 입출력으로 이름을 짓습니다. 예를 들어 요청별 메시지 생성 함수와 텍스트별 벡터 생성 함수를 구분합니다. 수량·시간의 단위와 순서·인덱스의 대상도 드러냅니다.
- 인터페이스 계약·외부 API·언어가 생성하는 접근자의 이름은 지킵니다. 고정된 이름만으로 역할이 부족하면 짧은 설명을 붙이고, 설명을 대신하려고 불필요한 위임 메서드를 추가하지 않습니다.
- Fluent API의 연속 호출은 호출 단계마다 줄바꿈합니다. receiver 또는 정적 생성 호출을 첫 줄에 두고, 이어지는 호출은 일정하게 들여써 한 줄에 하나씩 배치합니다. 짧다는 이유로 여러 단계를 한 줄에 합치지 않습니다. 코드와 문서의 Java 예제에 같은 기준을 적용합니다.
- 단순한 AssertJ 검증문은 `assertThat(criteria.maxPrice()).isEqualTo(15000);`처럼 한 줄로 유지합니다. 검증 대상 안의 짧은 접근 체인도 함께 둡니다. 람다 본문이나 여러 검증이 들어 있는 복합 검증은 블록 구조를 유지하며 한 줄로 압축하지 않습니다.
- 체인 줄바꿈은 호출 순서·인자·문자열·동작을 바꾸지 않습니다. 중첩 인자와 람다 블록의 들여쓰기를 함께 확인하고, JSON 등 구조화 데이터의 배열·하위 객체 경계를 드러냅니다.

```java
return client
        .prompt()
        .system(SYSTEM_INSTRUCTION)
        .user(question)
        .call()
        .content();
```
- 코드만으로 결과 구조를 떠올리기 어렵다면 생성 메서드 가까이에 들여쓴 결과 예시를 둡니다. Java에서는 메서드 Javadoc의 `<pre>{@code ...}</pre>`처럼 IDE에서도 구조가 보존되는 형식을 사용할 수 있습니다. 동적 값·고정값·조건부 필드와 전체 본문·일부 메시지의 차이를 짧게 밝힙니다. 자리표시자·설명용 주석을 넣은 구조 예시는 실행 가능한 JSON과 구분하며, 이름 변경 시 예시의 참조도 맞춥니다. 모든 단순 메서드에 큰 예시를 의무화하지 않습니다.

## 교육용 객체 설계와 SOLID 적용 수준

- SOLID는 책임과 변경 이유를 찾는 검토 기준으로 사용합니다. 모든 원칙을 모든 클래스에 적용하거나, 메서드 수만으로 잘못된 설계라고 판정하지 않습니다. 상속이 없다면 치환 원칙의 적용 범위도 그에 맞게 설명합니다.
- 서로 다른 이유로 바뀌는 처리와 독립된 상태·정책이 섞여 이해를 방해할 때 작은 객체로 분리합니다. 예를 들어 응답 순서 관리와 서버 생명주기, 설정 변경과 데이터 형식 생성은 분리 후보입니다. 한 곳에서만 쓰는 짧고 응집된 처리를 분리하기 위해 클래스 수를 늘리지 않습니다.
- 테스트가 쓰기 쉬운 공개 진입점은 여러 내부 객체에 위임할 수 있습니다. 사용 편의를 위한 공개 메서드와 그 구현 책임의 위치를 구분합니다. 실제 교체 필요나 검증상의 이점이 없는 인터페이스·상속 계층·범용 프레임워크를 도입하지 않습니다. 기존 함수·콜백이나 표준 타입으로 충분하면 활용합니다.
- 관련 설정·값은 의미 있는 타입으로 묶고, 배열 위치나 여러 곳의 전체 필드 재조립에 의미를 숨기지 않습니다. 변경·초기화 규칙은 해당 상태의 소유자에 모읍니다. 동시성 대응은 실제 필요한 보조 코드 안에 두며, 독립된 상태가 필요한 요청에는 일관된 스냅샷 등의 기존 보장을 유지합니다.
- 학습자가 핵심 흐름을 따라갈 수 있는지가 최종 판단 기준입니다. 설명을 쉽게 하려는 리팩터링이 미래 단원의 개념이나 여러 보조 클래스의 내부 구현을 필수 선수 지식으로 만들지 않게 합니다.

## 동작을 보존하는 리팩터링

- 이름·표현 정리, 책임 분리, 기능 변경을 구분합니다. 리팩터링에서는 기존 입력·출력·오류·상태 변화의 계약을 먼저 확인하고, 별도 요청 없는 기능·버전·실행 설정 변경을 섞지 않습니다.
- 가능한 한 학습 코드의 사용법을 유지합니다. 이름 변경이 필요하거나 요청되었다면 호출부·정적 import·메서드 참조·실행 예제·현재 안내를 함께 수정합니다. 과거 검증 기록의 당시 이름은 이력으로 구분합니다. 불필요한 구 API 별칭을 남겨 같은 기능의 이름을 늘리지 않습니다.
- 공통 보조 코드는 반복 통신·형식 처리·출력에 집중하고, 단원별 입력·시나리오·검증은 단원에 남깁니다. 이미 있는 [학습용 테스트 기준](#학습용-테스트)과 함께 적용합니다.
- 상태를 옮기면 초기화가 지우는 값과 유지하는 값, 응답 순서 소진, 요청 기록, 진행 중 작업에 설정 변경이 미치는 영향, 실패 결과를 보존합니다. 보호 복사·잠금 등을 제거할 때는 같은 보장이 유지되는지 확인합니다.
- 변경된 경계의 기존 동작 테스트부터 실행하고, 공통 API나 상태 관리가 바뀌면 영향을 받는 사용처까지 검증합니다. 구현 구조를 되풀이하는 테스트 대신 의미 있는 회귀 사례를 보강합니다. 출력과 assertion, 실제 외부 호출의 구분도 유지합니다.

## 학습용 테스트

- 테스트 클래스는 객체 기능의 단위 테스트, 로컬 대체 서버·모델을 사용하는 통합 테스트, 실제 외부 서비스의 Live 테스트를 이름으로 구분합니다. 구체적인 접미사와 선택 명령은 프로젝트 설정에 둡니다.
- 하나의 객체 기능을 Spring·웹 서버·외부 모델 없이 검사할 수 있다면 대상 객체별 단위 테스트로 분리합니다. HTTP 요청을 쓰지 않는다는 이유만으로 모델 어댑터·Advisor·도구 연결 검증까지 단위 테스트로 옮기지 않습니다. 기존 입력·정상·실패 검증과 결과 출력을 보존합니다.
- 대상 객체가 단순 위임만 하고 규칙은 다른 객체의 단위 테스트, 프레임워크 연결은 통합 테스트로 확인된다면 중복 단위 테스트를 강제하지 않습니다. 독립적인 인자 변환·분기·검증·상태 변경이 생기면 그 동작을 기준으로 테스트를 분리합니다.
- 테스트 분리·이름 변경 후 파일명·클래스명·문서 링크·선택 명령을 함께 맞추고, 로컬 실행 명령에 객체 단위 테스트와 모델 통합 테스트가 모두 포함되는지 확인합니다. 이름 구분을 위해 태그·추가 빌드 태스크를 의무화하지 않습니다.
- 준비 코드와 실제 실행을 혼동하기 쉬운 테스트에만 `Given: 준비 내용`, `When: 실행 내용`, `Then: 검증 내용` 주석을 사용합니다. 가짜 응답·도구 시나리오 설정, 이전 대화·저장 상태 준비, 호출 전후 계측 비교 등이 대상입니다. 짧고 역할이 분명한 단위 테스트나 단순 호출·검증에는 세 주석을 강제하지 않습니다.
- 단계 주석은 학습자 언어로 구체적인 의도를 설명하며, 실행 코드의 위치와 일치시킵니다. 응답 설정은 Given, API·서비스 호출은 When, 결과·호출 기록 확인은 Then입니다. 준비가 없는 테스트에 형식만 맞추려고 빈 Given이나 불필요한 변수·보조 메서드를 만들지 않습니다.
- 여러 시나리오·후속 요청이 이어지면 실제 흐름에 맞게 단계를 반복합니다. 이전 상태를 만드는 API 호출도 후속 동작을 검증하는 관점에서는 Given이 될 수 있으며, 중간 검증·출력·실패 후 상태 검사를 보존합니다. When을 assertion 안에서 꺼낼 때 같은 요청을 다시 실행하거나 호출 순서·횟수를 바꾸지 않습니다.
- 테스트 메서드명은 프로젝트의 학습자 언어로 읽기 쉽게 작성해, 이름만으로 조건과 기대 동작을 알 수 있게 합니다.
- 케이스 이름과 실제 응답·상태·검증 대상 값을 함께 출력합니다. 출력은 검증을 대체하지 않으며 기존 assertion을 유지합니다. 실패 결과도 assertion 전에 확인할 수 있게 합니다.
- 키·인증 헤더·비밀 설정을 출력하지 않습니다. 큰 벡터·문서의 일부만 출력하면 전체 길이와 생략 범위를 표시합니다.
- 외부 모델 연결을 배우는 실습에는 로컬 고정 응답 테스트와 별도 실제 제공 업체 Live 클래스를 제공합니다. 프로젝트의 기존 설정·실행 방식을 사용하고, 아직 배우지 않은 기능에 의존하는 예제를 만들지 않습니다.
- 실제 모델의 문구·도구 순서·요청 횟수를 고정 응답과 같다고 가정하지 않습니다. Live는 의미 있는 결과와 구조를 검증하며, 품질 평가 수업은 사례별 판정과 연결 실패를 구분합니다.
- Live 추가 후 로컬 검증 명령에 클래스 필터가 있는지 확인합니다. 학습자가 전체 테스트와 Live 선택 실행의 외부 호출 여부를 알 수 있게 안내합니다.

- 여러 실습에 반복되는 Mock 통신·프로토콜 포장·출력은 테스트 전용 공통 도구로 분리합니다. 학습 대상인 응답 값·시나리오 분기·검증은 단원에 남기고, 운영 코드와 Live의 연결에는 Mock 의존성을 추가하지 않습니다. 공통화 시 기록·초기화·비동기 지연 동작과 기존 검증 내용을 보존합니다.

## 쉬운 표현과 문서 분리

- 전문 용어는 쉬운 설명과 함께 소개합니다. 학습자가 할 행동을 구체적으로 씁니다.
- ‘각 행을 읽고 관찰’처럼 학습 범위나 행동이 모호한 표현을 피합니다.
- ‘작은 구현’이라고만 쓰지 말고 어떤 입력을 받아 무엇을 출력하는 실행 코드인지 밝힙니다.
- 긴 내부 동작과 심화 설명은 하위 보충 문서로 나눕니다. 본문 링크·권장 학습 시점·돌아가기 링크를 제공합니다.
- 기본 예제를 먼저, 도구 호출·복수 시스템·예외 등 복잡한 예제를 나중에 배치합니다.
- 교육 계획에는 대상·순서·목표·완료 기준을, 상세 수업에는 예제·프롬프트·실습 절차를 둡니다.
- 학습자 문서에 제작 회의, 개편 근거, 검토 과정이나 내부 승인 이력을 넣지 않습니다.
- 같은 설명을 반복하기보다 기준 문서를 정하고 연결합니다. 여러 문서를 따로 읽어도 필요한 최소 문맥은 제공합니다.
- 확인 질문은 해당 페이지의 코드·표·그림과 연결합니다. 문서 분리 후에도 ‘위·아래·앞서’가 가리키는 대상이 현재 페이지에 있는지 확인하고, 다른 페이지라면 실제 링크로 안내합니다.

원칙은 이 파일이 기준이고, 검토 시에는 [검토 질문](review.md)을 적용합니다. 템플릿·절차에는 필요한 작성 칸과 수행 단계만 둡니다.

## 변경과 완료

- 사용자가 조정한 순서·예제·표현을 보존합니다. 수정 요청 범위를 넘어 일괄 재작성하지 않습니다.
- 파일 이동이나 이름 변경 시 본문·보충 문서·실습·빌드 등록·명령·링크를 함께 확인합니다.
- 외부 자료는 정확성과 버전의 근거로 활용하고, 학습 흐름은 자체 교재로 설명합니다. 제공 업체의 규격과 프레임워크 공통 API를 구분합니다.
- 확인하지 않은 것을 일반적인 보장처럼 쓰지 않습니다. 현재 구현의 사실과 학습용 단순화를 구분합니다.
- 완료 기록에는 실행한 검사·결과·미검증 범위를 남깁니다. ‘실패·스킵 없음’ 대신 통과 수와 실패·건너뜀 수를 명확히 씁니다.
- 사용자의 계획·검토·수정 요청을 구분하며, 추가 승인 절차를 임의로 만들지 않습니다.
- 커밋은 프로젝트 설정의 언어·형식을 따릅니다. 제목만으로 끝내지 않고 본문에 주요 변경·검증 결과·미검증 범위를 요약합니다. 실행하지 않은 검증을 통과로 쓰지 않습니다.
