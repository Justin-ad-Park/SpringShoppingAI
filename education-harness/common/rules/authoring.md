# 교육 문서와 샘플 코드 작성 원칙

## 설명 수준과 순서

- 대상 독자와 선수 지식은 프로젝트 설정을 기준으로 합니다.<br>
  해당 기술의 전문 용어를 이미 안다고 가정하지 않습니다.
- 한 소수업에서는 주요 새 개념 하나를 다룹니다.<br>
  새 개념을 배우기 위해 아직 설명하지 않은 다른 동작까지 함께 이해해야 한다면 예제를 나눕니다.<br>
  앞 단계에서 확인한 동작을 바탕으로 다음 단계에서 새 기능을 추가하고, 문제 → 개념 → 필요한 그림 → 코드 → 실행 → 결과 해석으로 연결합니다.
- 프레임워크 사용법을 가르칠 때는 문제·용어·역할을 설명하고, 관련 제공 기능과 구현 클래스의 최소 사용 예제부터 제시합니다.<br>
  커스텀 구현은 추가로 해결할 요구가 있을 때 별도 단계로 설명하고, 필요한 조합·심화로 이어갑니다.<br>
  제공되는 부분과 개발자가 작성하는 부분을 구분하며, 직접 구현 원리 자체가 목표인 수업은 순서를 조정할 수 있습니다.<br>
  목표에 필요한 기능만 소개하고 전체 API 목록이나 커스텀 구현을 모든 수업에 요구하지 않습니다.
- 새 문법과 프레임워크 기능을 구분합니다.<br>
  필요한 문법은 먼저 짧게 설명합니다.
- 처음 보는 기능을 설명하기 위해 아직 배우지 않은 기능을 선행 의존성으로 사용하지 않습니다.
- 설명을 나눌 때는 코드의 실행 가능성을 유지합니다.<br>
  장황한 추상화나 공통 프레임워크로 학습 코드를 감추지 않습니다.
- 전체 소스·일부 발췌·구조 설명용 예시를 구분합니다.<br>
  생략한 생성·설정 코드가 있으면 어디에서 준비되는지 안내합니다.
- 다른 모델·도구·서버가 등장하면 누가 판단하고 누가 실행하며 무엇이 전송되는지 설명합니다.

## 목표에 맞는 설명과 배치

- 수업에서 해결할 문제와 학습자가 이해하거나 할 수 있게 될 행동을 먼저 정하고, 예제는 그 목표를 지원하도록 선택합니다.<br>
  기존 코드에 맞춰 목표를 역으로 정하거나, 코드·클래스의 위치 찾기, 타입·변수·내부 메서드 나열, “무엇을 하지 않는다”는 구분으로 목표를 대신하지 않습니다.
- 제목 → 목표 → 도입 → 예제 → 확인 질문이 같은 개념을 다루는지 대조합니다.<br>
  기능과 설명의 학습 역할을 확인해 현재 단계에 유지할지, 축약하거나 다른 단계로 옮길지, 삭제할지 판단합니다.<br>
  목표 밖의 기능을 분리할 때는 그 기능의 상태·프롬프트·응답 필드·테스트·설명도 함께 검토하되, 기본 개념의 이해에 필요한 설명까지 제거하지 않습니다.<br>
  소수업 목표를 바꾸면 부모 목차의 완료 기준도 맞추고, 교육 계획의 해당 설명과 충돌하는지 확인합니다.
- 설명은 대상 독자의 개념 이해, 사용 이유, 코드 흐름, 실행 또는 결과 해석에 어떤 역할을 하는지 판단합니다.<br>
  학습 목표를 API 실행법만으로 좁히지 않습니다.<br>
  역할이 불명확하면 삭제하지 않고 사용처와 선수 지식을 확인한 뒤 유지·축약·이동·삭제를 결정합니다.<br>
  뒤에서 필요한 설명은 해당 기능을 배우는 위치로 옮기고, 그곳에 실제 설명과 진입 경로가 있는지 확인합니다.
- 용어의 정의, 기능을 사용하는 이유, 입력·출력 예시, 단계 사이에 전달되는 데이터, 결과 읽는 방법은 교육 설명입니다.<br>
  실행에 직접 필요하지 않거나 소스 링크가 있다는 이유로 생략하지 않습니다.<br>
  이미 배운 내용도 현재 예제를 읽는 데 필요하면 짧게 복습하고 상세 설명으로 연결합니다.<br>
  선택 보충도 앞 수업과 구분되는 학습 목적이 있어야 합니다.<br>
  기존 기능의 조합을 반복하는 정도라면 고유한 설명·검증이 있는지 확인한 뒤 기존 수업에 통합할지 판단합니다.<br>
  전체 소스 나열은 주요 흐름의 해설을 대신하지 않습니다.
- 학습과 무관한 정보는 현재 학습이나 연결된 후속 학습에 기여하지 않는 제작·편집 이력, 미사용 기능 조사 내역, 의미가 같은 반복 등입니다.<br>
  길이·부정문·특정 단어만으로 분류하지 않습니다.<br>
  중요한 오해를 막는 설명은 유지합니다.
- 조사·검증 과정에서 확인한 사실을 모두 본문에 옮기지 않습니다.<br>
  미사용 클래스, 폐기 예정 이름, 배포 여부, 문서 주소의 변경 가능성은 현재 실습의 선택·실행·결과 해석에 영향을 주거나 사용자가 해당 목록·이력의 검토를 요청한 경우에 설명합니다.<br>
  사실이라는 이유나 막연한 오해 가능성만으로 새 용어·주의사항을 덧붙이지 않습니다.
- 출처는 참고 자료에 식별 가능한 링크와 필요한 범위의 설명으로 남깁니다.<br>
  작성자가 수행한 상세 버전 대조·검증 과정은 기록이 필요할 때 검증 기록에 둡니다.<br>
  현재 예제의 실행이나 해석에 영향을 주는 버전 차이는 해당 동작 옆에서 설명합니다.
- 예제의 입력 조건·계산 정책·조건 누락 같은 세부 규칙은 해당 필드를 사용하거나 검증하는 부분에서 설명합니다.<br>
  설명 순서는 학습 목표에 맞춥니다.<br>
  정상 동작을 처음 배우는 수업에서는 기본 흐름을 먼저 설명하고, 실패·복구가 주제인 수업에서는 필요한 정상 동작을 짧게 복습한 뒤 실패 사례를 중심으로 구성합니다.<br>
  목표에 필요하지 않은 동시성·확장 설계는 뒤 소수업이나 선택 보충으로 배치합니다.<br>
  나눠 보여주는 코드는 전체·발췌·구조 예시를 구분하고 완전한 실행 소스와 테스트로 연결합니다.
- 설명을 삭제·축약·이동하기 전에 개념 정의·사용 이유·단계 연결·결과 해석이 빠지지 않는지와 현재 예제를 잘못 이해하거나 실행하게 될 조건이 사라지지 않는지 확인합니다.<br>
  현재 목표에 필요한 동작·계산 조건, 실행 비용, 실패 후 상태, 검증 범위의 한계는 해당 동작 옆에 유지합니다.<br>
  문장의 삭제·이동 여부는 길이나 특정 단어가 아니라 수업 목표와의 관계로 판단합니다.

## 설명의 근거와 동작 범위

- 설명하는 동작은 제시한 코드에서 확인할 수 있어야 합니다.<br>
  생성자만으로 요청별 재사용을 설명하는 것처럼 근거가 생략되어 있다면 필요한 필드·메서드를 함께 보여주거나 실제 소스로 연결합니다.
- 구현을 다루는 소수업에서는 해당 구현 클래스·핵심 메서드·관련 테스트로 직접 연결합니다.<br>
  예제가 여러 개면 목차나 실습 README에 소수업–구현–테스트 대응을 간단히 제시하고, 본문에서는 현재 단계의 코드로 연결합니다.<br>
  개념 수업에 실행 샘플이 없으면 그 범위를 밝힙니다.
- 객체 생성, 요청 구성, 실제 외부 호출, 결과 읽기를 구분합니다.<br>
  호출·반복은 무엇을 한 번으로 세는지와 어떤 구간이 다시 실행되는지 밝힙니다.<br>
  “감싼다” 같은 요약 표현은 실제 호출·반환 시점과 연결해 설명합니다.<br>
  메서드 이름만으로 실행 시점을 추정하지 않고 사용 버전의 구현·공식 근거를 확인합니다.
- 직접 제어 코드를 만들기 전에 사용 버전의 기본 제공 기능과 설정을 확인합니다.<br>
  샘플이 기본 제공 기능과 다르게 동작한다면 그 기능의 역할과 동작을 먼저 소개하고, 샘플에서 다르게 구현한 요구사항·선택 이유와 정상·실패 시 차이를 설명합니다.<br>
  직접 구현을 라이브러리 기능으로 바꿀 때도 저장·변경 시점, 실패 뒤 남는 상태, 예외 처리 범위가 같은지 확인합니다.<br>
  샘플의 선택을 프레임워크가 요구하는 동작처럼 설명하지 않습니다.
- 성공·검증 완료 같은 상태 이름에는 통과한 검사와 확인하지 않은 범위를 명시합니다.<br>
  결과 상태는 반환값뿐 아니라 필요한 작업의 수행 여부를 근거로 정합니다.<br>
  예를 들어 검색을 정상 수행했으나 조건에 맞는 항목이 없는 경우와 필요한 검색·계산을 수행하지 않은 경우를 구분합니다.<br>
  빈 목록이나 0원의 의미는 해당 업무의 성공 조건에 따라 판단합니다.<br>
  형식·ID·값 검사 통과를 요청 전체 처리 완료나 내용의 정확성 보장으로 확대하지 않습니다.
- 예상하지 못한 예외를 일반적인 실패 응답으로 바꿀 때는 원인 파악에 필요한 정보를 보존합니다.<br>
  기존 예외 전달·로그·관측 수단 중 예제에 적합한 방법을 사용하며, 처리 위치와 오류 종류를 확인할 수 있게 합니다.<br>
  인증 정보와 진단에 불필요한 요청·응답 원문은 기록하지 않습니다.

## 설정과 실행 환경

- 같은 실행 범위에서 공유하는 설정은 기준 위치를 정하고 중복 선언을 줄입니다.<br>
  테스트에는 검증 조건을 만들거나 실행 환경을 분리하는 데 필요한 설정을 둡니다.<br>
  독립 실행하는 예제 사이에는 중복 제거만을 목적으로 공통 설정 의존성을 추가하지 않습니다.
- 설정값의 비교가 동작을 결정한다면 무엇과 비교하며 결과가 어떻게 달라지는지 설명합니다.<br>
  앞 단계와 다른 기본값·상수·비교 기준이 등장하면 실행 결과를 예상하는 데 필요한 관계부터 설명합니다.
- 같은 동작에 영향을 주는 설정이 여러 위치에 있으면 사용 버전의 적용 범위와 우선순위를 확인합니다.<br>
  설정을 변경할 때는 의도한 값이 실제 동작에 반영되는지 관련 테스트나 실행 결과로 확인합니다.<br>
  확인을 위해 비밀 설정을 출력하지 않습니다.

## 실행 가능한 예제

- 구현 수업은 동작하는 코드, 필요한 설정, 실행 위치, 명령, 기대 결과와 테스트를 함께 제공합니다.
- 개념 수업은 실행 코드가 없어도 됩니다.<br>
  실행을 제공하지 않은 예제를 완성된 실습이라고 표현하지 않습니다.
- 기본 예제는 가장 단순한 정상 흐름을 보여주며 선택 심화 기능 없이 독립 실행되어야 합니다.<br>
  확장은 변경 규모와 학습 순서에 따라 같은 코드의 설정 변경·추가 테스트·별도 예제 중 적절한 방식으로 제공합니다.<br>
  모듈 분리를 일괄 요구하지 않습니다.
- 소수업으로 설명을 나누면 실행 코드도 그 단계에 필요한 기능을 읽고 실행할 수 있게 구성합니다.<br>
  문서만 분리한 채 미래 단계의 기능·상태·설정을 한 실행 흐름에 섞지 않습니다.<br>
  코드 분리 단위는 줄 수보다 읽기 부담과 의존성·설정·실행 환경의 독립성으로 정하며, 소수업마다 진입점·설정·테스트 클래스를 복제할 필요는 없습니다.
- 학습 목표를 직접 확인하는 데 도움이 되는 경우 작은 수행 과제를 제공합니다.<br>
  변경하거나 판단할 대상, 수행 방법, 확인할 결과를 명시합니다.<br>
  개념 수업에는 설명·분류·예측 과제를 사용할 수 있으며 모든 단원에 코드 수정 과제를 의무화하지 않습니다.
- 코드 변경 과제와 비교 실험은 수정 전 결과 확보 → 하나 변경 → 필요시 재시작·재적재 → 같은 입력으로 비교 → 원복 순서로 안내합니다.<br>
  무엇을 어디에서 확인할지 응답 필드·로그·테스트 검증문 등 실제 경로를 제시합니다.
- 실험 데이터로 기대한 차이를 확인할 수 있는지 검사합니다.<br>
  현재 출력에 없는 횟수나 내부 입력을 응답 문장만으로 추정하게 하지 않습니다.
- 실패 처리 자체가 학습 목표이거나 정상 동작만으로는 사용법을 오해할 수 있는 경우에 실패 사례를 보여줍니다.<br>
  그 외에는 실패 사례를 생략할 수 있습니다.<br>
  보조 서버·동시성·추적 코드가 필수 선수 지식이 되지 않게 합니다.
- 모델의 자연어 응답을 고정 문자열과 비교하지 않습니다.<br>
  고정 응답 서버의 연결 검증과 실제 모델 품질 평가를 구분합니다.<br>
  로컬 테스트 통과는 확인한 연결·분기·값의 근거로만 기록하며 실제 외부 연결 성공이나 모델 품질까지 확대하지 않습니다.
- 테스트는 실제로 확인하려는 동작을 검증합니다.<br>
  구현을 그대로 되풀이하는 테스트나 사소한 문장 수정용 테스트를 만들지 않습니다.
- 코드와 문서의 버전·설정 이름·실행 경로를 대조합니다.<br>
  버전 확인 위치는 프로젝트 설정을 따릅니다.

## 읽기 쉬운 이름과 코드 표현

변수·상수·타입·메서드·패키지의 이름은 [역할을 드러내는 이름](naming.md)을 기준으로 작성·검토합니다.<br>
역할·측정값·상태·외부 계약을 확인하는 상세 절차와 예시는 그 문서에서만 관리합니다.

- 코드의 줄바꿈·들여쓰기·주석 형식은 대상 언어와 프로젝트 관례를 따릅니다.<br>
  표현을 정리할 때 호출 순서·인자·문자열·동작을 바꾸지 않습니다.
- 코드만으로 결과 구조를 떠올리기 어렵다면 생성 코드 가까이에 들여쓴 결과 예시를 둡니다.<br>
  전체·발췌·설명용 구조를 구분하고, 동적 값과 생략 범위를 밝힙니다.<br>
  단순한 메서드마다 큰 예시를 의무화하지 않습니다.

## 교육용 객체 설계와 SOLID 적용 수준

- SOLID는 책임과 변경 이유를 찾는 기준으로 사용합니다.<br>
  원칙의 형식이나 메서드 수만으로 설계를 판단하지 않습니다.
- 서로 다른 책임·상태 정책이 섞여 이해를 방해할 때 분리합니다.<br>
  실제 교체 필요나 검증상의 이점이 없는 인터페이스·상속·범용 계층을 추가하지 않습니다.<br>
  공개 진입점의 편의성과 내부 구현 책임은 구분합니다.
- 학습자가 핵심 흐름을 따라가기 쉬워지는지가 최종 판단 기준입니다.<br>
  여러 보조 클래스나 미래 단원의 개념을 필수 선수 지식으로 만들지 않습니다.

- 상태 공유로 생기는 문제를 설명할 때는 어떤 객체를 여러 요청이 함께 사용하며, 그중 어떤 값이 언제 변경되는지 명시합니다.<br>
  변경되지 않는 설정과 요청마다 달라지는 상태를 구분하고, API 이름·등록 위치·멤버 변수의 존재 자체를 문제의 원인으로 단정하지 않습니다.

## 동작을 보존하는 리팩터링

- 이름·표현 정리, 책임 분리, 기능 변경을 구분합니다.<br>
  리팩터링에서는 기존 입력·출력·오류·상태 변화의 계약을 먼저 확인하고, 별도 요청 없는 기능·버전·실행 설정 변경을 섞지 않습니다.<br>
  오류 수정은 의도적으로 바뀌는 동작과 이를 확인하는 회귀 검증을 명시합니다.
- 가능한 한 학습 코드의 사용법을 유지합니다.<br>
  이름 변경이 필요하거나 요청되었다면 호출부·정적 import·메서드 참조·실행 예제·현재 안내를 함께 수정합니다.<br>
  과거 검증 기록의 당시 이름은 이력으로 구분합니다.<br>
  불필요한 구 API 별칭을 남겨 같은 기능의 이름을 늘리지 않습니다.
- 상태의 소유자를 옮기거나 동시성 처리를 바꿀 때도 기존 초기화·실행 순서·실패 후 상태의 보장을 유지합니다.
- 변경된 경계의 기존 동작 테스트부터 실행하고, 공통 API나 상태 관리가 바뀌면 영향을 받는 사용처까지 검증합니다.<br>
  구현 구조를 되풀이하는 테스트 대신 의미 있는 회귀 사례를 보강합니다.<br>
  출력과 assertion, 실제 외부 호출의 구분도 유지합니다.

## 학습용 테스트

- 테스트 클래스는 객체 기능의 단위 테스트, 로컬 대체 서버·모델을 사용하는 통합 테스트, 실제 외부 서비스의 Live 테스트를 이름으로 구분합니다.<br>
  구체적인 접미사와 선택 명령은 프로젝트 설정에 둡니다.
- 하나의 객체 기능을 Spring·웹 서버·외부 모델 없이 검사할 수 있다면 대상 객체별 단위 테스트로 분리합니다.<br>
  HTTP 요청을 쓰지 않는다는 이유만으로 모델 어댑터·Advisor·도구 연결 검증까지 단위 테스트로 옮기지 않습니다.<br>
  기존 입력·정상·실패 검증과 결과 출력을 보존합니다.
- 대상 객체가 단순 위임만 하고 규칙은 다른 객체의 단위 테스트, 프레임워크 연결은 통합 테스트로 확인된다면 중복 단위 테스트를 강제하지 않습니다.<br>
  독립적인 인자 변환·분기·검증·상태 변경이 생기면 그 동작을 기준으로 테스트를 분리합니다.
- 테스트 분리·이름 변경 후 파일명·클래스명·문서 링크·선택 명령을 함께 맞추고, 로컬 실행 명령에 객체 단위 테스트와 모델 통합 테스트가 모두 포함되는지 확인합니다.<br>
  이름 구분을 위해 태그·추가 빌드 태스크를 의무화하지 않습니다.
- 준비·실행·검증의 구분이 학습에 도움이 될 때만 Given·When·Then 주석을 사용합니다.<br>
  주석은 실제 단계와 맞추며, 형식을 위해 준비 코드나 보조 메서드를 늘리지 않습니다.
- 사용자 관점의 예제와 Live 테스트는 실제 사용자가 말할 요청을 사용합니다.<br>
  특정 도구 사용을 유도하려고 고객 메시지에 내부 메서드명·호출 순서·객체 전달 형식을 넣지 않습니다.<br>
  도구 계약 자체를 검사하는 기술적인 입력은 사용자 관점의 시나리오와 구분합니다.
- 테스트 메서드명은 프로젝트의 학습자 언어로 조건과 기대 동작을 드러냅니다.<br>
  호출 기록·반환값·모델에 전달된 데이터·최종 답변의 정확성을 구분하고, 테스트 이름과 설명은 실제 검증문으로 확인한 범위까지만 주장합니다.
- 학습에 필요한 실제 응답·상태·검증 대상 값을 출력하되, 출력이 assertion을 대신하지 않게 합니다.<br>
  결과 확인에는 기존 출력·반환값·호출 기록 중 이해하기 쉬운 방법을 사용합니다.<br>
  확인만을 위해 별도 상태 전달이나 응답 구조를 추가할 때는 학습 목표에 필요한지 먼저 판단합니다.<br>
  출력 형식과 공통 지원 도구의 사용 방식은 프로젝트 설정을 따릅니다.
- 키·인증 헤더·비밀 설정을 출력하지 않습니다.<br>
  큰 벡터·문서의 일부만 출력하면 전체 길이와 생략 범위를 표시합니다.
- 실제 모델이나 서비스의 연결·동작이 학습 목표에 포함되면 대표 흐름을 실행하는 별도 Live 테스트를 작성합니다.<br>
  기존 Live 테스트가 같은 동작을 검증하면 그 테스트로 연결합니다. 실제 모델·서비스 연결이 학습 대상이 아닌 순수 로직·고정 응답 전용 예제에는 Live 테스트를 추가할 필요가 없습니다.<br>
  Live가 필요한 예제는 코드와 실행 조건을 제공합니다. 실행 범위는 [검증 절차](../workflows/verify-materials.md#4-테스트와-빌드)를 따릅니다.<br>
  아직 배우지 않은 기능에 의존하는 예제를 만들지 않습니다.
- 실제 모델의 문구·도구 순서·요청 횟수를 고정 응답과 같다고 가정하지 않습니다.<br>
  Live는 의미 있는 결과와 구조를 검증하며, 품질 평가 수업은 사례별 판정과 연결 실패를 구분합니다.
- 테스트 실행 명령에는 외부 서비스 호출 여부를 안내합니다.<br>
  대상 선택 방식은 프로젝트 설정을 따릅니다.
- 여러 실습에 반복되는 Mock 통신·프로토콜 포장·출력은 테스트 전용 공통 도구로 분리합니다.<br>
  학습 대상인 응답 값·시나리오 분기·검증은 단원에 남기고, 운영 코드와 Live의 연결에는 Mock 의존성을 추가하지 않습니다.

## 설명 주체와 대상 명시

- 동작의 주체와 대상을 명시합니다.<br>
  ‘클래스·메서드·설정’처럼 여러 대상을 가리킬 수 있는 표현은 역할이나 실제 API 이름을 붙입니다.<br>
  예: ‘클래스’ → ‘Advisor 구현 클래스’, ‘등록 메서드’ → ‘등록 메서드(defaultAdvisors 또는 advisors)’.
- ‘경계를 고려한다’, ‘적절히 처리한다’처럼 독자가 동작 결과를 예상하기 어려운 표현은 적용 조건·입력·처리 방법·결과가 드러나게 풀어 씁니다.<br>
  처음 배우는 동작에서 문장만으로 이해하기 어렵다면 작은 입력 예시와 처리 전후 결과를 함께 보여줍니다.<br>
  이미 설명한 동작마다 예시나 표를 반복할 필요는 없습니다.
- 비교·요약 문장에서도 핵심 대상을 생략하지 않습니다.<br>
  앞에서 설명했더라도 무엇과 무엇을 비교하는지, 누가 무엇을 처리하는지 문장에서 식별할 수 있게 씁니다.
- 약칭은 의미가 하나로 유지될 때만 사용합니다.<br>
  ‘기본 제공’과 ‘기본 설정’처럼 다른 뜻을 같은 약칭으로 줄이지 않습니다.<br>
  약칭을 도입할 때는 원래 용어와 대응 관계를 먼저 밝힙니다.<br>
  같은 개념의 대표 용어는 프로젝트 설정의 지정 위치 한 곳에서 관리하고, 교재·목차·실습 안내·코드 설명·테스트 이름에 일관되게 사용합니다.<br>
  라이브러리 API 이름과 서로 다른 개념까지 표기를 맞추기 위해 변경하지 않습니다.
- 전체 이름의 반복 여부보다 독자가 대상을 식별할 수 있는지를 기준으로 판단합니다.<br>
  매 문장에 전체 이름을 반복할 필요는 없지만, 초보자가 주체나 지시 대상을 추측해야 한다면 구체적인 이름을 다시 씁니다.

## 쉬운 표현과 문서 분리

- Markdown 설명 문단과 목록 항목에서 문장이 이어지면 문장 끝에 `<br>`를 붙이고 소스에서도 줄을 바꿉니다.<br>
  문단이나 목록 항목의 마지막 문장에는 붙이지 않으며, 주제가 달라지면 빈 줄로 문단을 나눕니다.<br>
  문장 종결 마침표를 기준으로 하고 버전 번호·API 이름·URL·인라인 코드 안의 마침표는 보존합니다.<br>
  제목·표·코드 블록·평가용 원본 입력은 일괄 변환하지 않습니다.
- 전문 용어는 쉬운 설명과 함께 소개합니다.<br>
  학습자가 할 행동을 구체적으로 씁니다.
- ‘각 행을 읽고 관찰’처럼 학습 범위나 행동이 모호한 표현을 피합니다.
- ‘작은 구현’이라고만 쓰지 말고 어떤 입력을 받아 무엇을 출력하는 실행 코드인지 밝힙니다.
- 긴 내부 동작과 심화 설명은 하위 보충 문서로 나눕니다.<br>
  본문 링크·권장 학습 시점·돌아가기 링크를 제공합니다.
- 기본 예제를 먼저, 도구 호출·복수 시스템·예외 등 복잡한 예제를 나중에 배치합니다.
- 교육 계획에는 대상·순서·목표·완료 기준을, 상세 수업에는 예제·프롬프트·실습 절차를 둡니다.
- 학습자 문서에 제작 회의, 개편 근거, 검토 과정이나 내부 승인 이력을 넣지 않습니다.
- 같은 설명을 반복하기보다 기준 문서를 정하고 연결합니다.<br>
  여러 문서를 따로 읽어도 필요한 최소 문맥은 제공합니다.
- 확인 질문은 해당 페이지의 코드·표·그림과 연결합니다.<br>
  문서 분리 후에도 ‘위·아래·앞서’가 가리키는 대상이 현재 페이지에 있는지 확인하고, 다른 페이지라면 실제 링크로 안내합니다.

## 확인 질문과 해설

- 수업에서 배운 작동 원리·판단 근거·사용법·결과 해석을 묻습니다.<br>
  샘플 고유의 클래스명·메서드명·상태 문자열·코드 위치를 찾거나 외우는 것만으로 답이 끝나는 질문은 피합니다.<br>
  구체적인 코드와 설정은 원리를 설명하는 근거로 사용할 수 있습니다.
- 프레임워크가 제공하는 API·설정·메타데이터와 샘플에서 정한 업무 정책·응답 형식을 구분합니다.<br>
  샘플 정책을 묻는다면 이름 자체보다 그 정책을 둔 이유와 변경 시 결과를 묻습니다.
- 실습 준비·언어 문법·테스트 읽기가 명시한 목표인 보충은 해당 목표를 확인하는 질문을 사용할 수 있습니다.<br>
  모든 질문을 프레임워크 API 암기로 통일하지 않습니다.
- 수업의 이해를 확인하는 질문 절은 `## 확인 질문`으로 통일합니다.<br>
  `여기서 멈춰 확인하기` 같은 별도 제목이나 답 없는 질문 절을 중복해서 두지 않습니다.<br>
  기존 질문이 여러 절에 흩어졌다면 하나로 모으고 해설을 보완합니다.
- 질문 바로 아래에 모든 답을 하나의 `<details>`로 모으고 `<summary>해설</summary>`을 사용합니다.<br>
  `open` 속성 없이 기본으로 접어 둡니다.<br>
  질문마다 별도 접기 영역을 만들지 않습니다.
- 질문이 여러 개면 질문과 답 모두 번호 목록으로 작성하고, 각 답을 같은 번호의 질문에 대응시킵니다.<br>
  질문이 하나면 번호를 생략할 수 있습니다.<br>
  완료 기준이나 참고 링크는 답과 구분합니다.
- 해설은 결론 → 적용 대상과 범위 → 이유 순으로 답합니다.<br>
  샘플 실행 횟수나 상태값은 개념 설명에 필요할 때 근거와 함께 덧붙이며, 이를 일반적인 보장으로 설명하지 않습니다.<br>
  질문에서 특정한 API 반환값·설정·계층을 해설에서도 유지합니다.
- 횟수·시간을 묻는다면 무엇을 세거나 측정하는지와 누적 범위를 밝힙니다.<br>
  정확한 수치를 결정하는 도구 루프·재시도·종료 조건 등 필요한 전제를 질문 가까이에 제시합니다.<br>
  사용자 요청·프레임워크 호출·모델 HTTP 요청·도구 실행 횟수를 같은 것으로 취급하지 않습니다.
- 질문에서 특정 설정·코드·수치·상태를 판단하게 한다면 그 대상을 이름과 값·단위로 명시하고, 필요한 설정이나 코드 발췌를 질문 바로 앞에 보여줍니다.<br>
  “이 설정”, “2회”처럼 대상이나 범위가 여러 가지로 해석될 표현만으로 묻지 않습니다.
- 질문을 제공한다면 이 페이지의 내용으로 확인할 수 있는 답을 함께 제공합니다.<br>
  목차·실행 안내·선택 참고 문서에 이 형식을 맞추기 위한 질문을 새로 만들지는 않습니다.<br>
  본문 중간의 설명용 의문문이나 실행 지시는 확인 질문 절과 구분합니다.

원칙은 이 파일이 기준이고, 검토 시에는 [검토 질문](review.md)을 적용합니다.<br>
템플릿·절차에는 필요한 작성 칸과 수행 단계만 둡니다.

## 변경과 완료

- 사용자가 조정한 순서·예제·표현을 보존합니다.<br>
  수정 요청 범위를 넘어 일괄 재작성하지 않습니다.
- 파일 이동이나 이름 변경 시 본문·보충 문서·실습·빌드 등록·명령·링크를 함께 확인합니다.
- 외부 자료는 정확성과 버전의 근거로 활용하고, 학습 흐름은 자체 교재로 설명합니다.<br>
  제공 업체의 규격과 프레임워크 공통 API를 구분합니다.
- 확인하지 않은 것을 일반적인 보장처럼 쓰지 않습니다.<br>
  현재 구현의 사실과 학습용 단순화를 구분합니다.
- 완료 근거의 작성 여부와 형식은 [검증 절차](../workflows/verify-materials.md#6-완료-근거)를 따릅니다.
- 사용자의 계획·검토·수정 요청을 구분하며, 추가 승인 절차를 임의로 만들지 않습니다.
- 커밋은 프로젝트 설정의 언어·형식을 따릅니다.<br>
  제목만으로 끝내지 않고 본문에 주요 변경·검증 결과·미검증 범위를 요약합니다.<br>
  실행하지 않은 검증을 통과로 쓰지 않습니다.
