# 기존 도구로 검증하기

이 절차는 전용 Python 프로그램이나 CI 설치를 요구하지 않습니다.
도구 호출과 결과를 실제로 확인하고, 프로젝트 설정의 명령을 사용합니다.

## 1. 범위와 실행 명령 확인

- `git status --short`로 기존 변경을 확인합니다. 사용자 변경을 덮어쓰지 않습니다.
- 프로젝트 설정에서 단원·실습·테스트 클래스·Live 포함 여부를 확인합니다.
- 문장 수정, 파일 이동, 코드 변경에 필요한 검사 범위를 먼저 정합니다.
- 비밀 설정값을 읽어 출력하지 않습니다. 실제 외부 호출은 요청된 검증 범위와 프로젝트 실행 방식을 따릅니다.

## 2. 문서와 코드 대조

기존 파일 검색·읽기·비교 도구로 확인합니다. CLI를 사용할 때의 기본 도구는 다음과 같습니다.

```bash
git diff --check
git diff --stat
```

검색은 `rg --files`와 `rg -n`을 우선 사용합니다. 대상 경로와 검색어는 실제 변경에 맞게 지정합니다.

- 본문·보충·실습·빌드 등록·README·명령에서 이전 경로가 남았는지 검색합니다.
- 로컬 Markdown 링크의 상대 경로와 제목 앵커를 대상 파일에서 확인합니다. 파일 존재 검사만 했다면 앵커까지 검사했다고 쓰지 않습니다.
- 외부 링크의 사실·버전이 이번 작업의 근거라면 공식 원문을 확인합니다.
- 전체 코드 블록은 실제 파일과 비교하고, 발췌 코드는 해당 부분과 비교합니다. 모든 코드 블록에 전체 파일 일치를 강제하지 않습니다.
- 메서드 이름 변경 시 선언·호출·정적 import·메서드 참조를 검색하고, 현재 예제·Javadoc·안내도 대조합니다. 과거 기록과 현재 사용 예를 구분합니다.
- Fluent 줄바꿈은 코드·문서 예제에 같은 기준인지 확인합니다. 단순 assertThat 한 줄과 복합 람다 블록의 예외를 대조하고, 표시 형식만 바꾼 코드는 호출 순서·인자·문자열이 유지되는지 확인합니다.
- 구조화 데이터 예시를 해당 생성 코드·입력과 대조합니다. 실제 JSON 예시는 파싱 가능한지, 자리표시자가 있는 구조 예시는 그 사실이 표시되어 있는지 확인합니다.
- 보충 문서에는 진입·복귀 링크와 권장 시점이 있는지 확인합니다.
- 목표와 도입·예제·확인 질문 및 부모 목차의 대응을 확인합니다. 부가 설명을 옮긴 뒤 필요한 계산 조건·비용·실패 상태·검증 한계와 완전한 실행 소스·테스트 연결이 남아 있는지 확인합니다.
- 설명별로 근거가 되는 코드 위치를 찾습니다. 객체 생성·요청 구성·실행·결과 읽기를 구분하고, 현재 페이지에서 확인할 수 없는 근거는 실제 소스 링크를 따라 대조합니다.
- 구현 대체를 설명한다면 저장·변경 시점과 실패 후 상태도 비교합니다. 오류 코드 설명은 실제 예외 처리 범위와, 검증 상태 설명은 실제 검사 항목과 대조합니다.
- 비교 실험의 입력·데이터가 차이를 만들 수 있는지 확인합니다. 예를 들어 문서 한 조각만 적재된 상태에서는 검색 상한을 늘려도 결과 수가 늘지 않습니다. 관찰할 값의 응답·로그·테스트 위치도 확인합니다.

반복 확인을 위해 도구가 한 번에 여러 파일을 열거나 검색하도록 묶을 수 있습니다. 저장소에 별도 검사 프로그램을 추가할 필요는 없습니다.

## 3. 그림 확인

Mermaid를 쓰는 프로젝트라면 사용 가능한 Mermaid 미리보기나 파서로 변경한 그림을 확인합니다.
사용한 도구와 문법·렌더링 중 무엇을 확인했는지 남깁니다.
도구가 없으면 미검증으로 남기고, 추측을 파서 통과로 기록하지 않습니다.
문법이 맞아도 코드와 그림의 판단 주체·호출 경계·순서는 따로 검토합니다.

## 4. 테스트와 빌드

- 프로젝트 설정에 지정된 로컬 검증 명령을 변경 모듈부터 실행합니다.
- 기본 테스트에 실제 외부 호출이 포함되면 로컬 클래스·대상을 명시합니다. 테스트 태그나 새 빌드 태스크를 임의 도입하지 않습니다.
- 빌드 성공, 실행한 테스트 수, 실패·오류·건너뜀 수를 결과에서 확인합니다. 소스 파일의 테스트 개수를 세어 실제 실행 수로 대신하지 않습니다.
- 캐시·up-to-date 재사용 여부를 구분합니다. 실행을 새로 확인해야 할 근거가 있을 때 재실행합니다.
- 같은 모듈의 테스트를 IDE와 CLI에서 동시에 실행하지 않습니다.
- 책임·상태 관리 리팩터링은 초기화·순차 응답·기록·실패·진행 중 설정 변경 등 실제 변경된 계약을 기존 테스트로 확인합니다. 공통 API를 바꾸면 영향을 받는 사용처의 컴파일과 관련 동작도 확인합니다.
- 변경·실패·우려가 없는 경우 불필요하게 전체 회귀를 반복하지 않습니다.

- 테스트를 분리하거나 이름을 바꾸면 객체 단위·모델 통합·Live 구분과 기존 검증 보존을 확인하고, 로컬 명령이 단위·통합 클래스를 빠짐없이 선택하는지 대조합니다. 본문·README·메서드 선택 명령도 함께 검색합니다.
- Live 코드는 컴파일과 실제 외부 호출을 구분해 기록합니다. 외부 호출을 하지 않은 채 Live 통과로 표시하지 않습니다.

## 5. 하네스 자체를 바꿨다면

교재 테스트와 별도로 [행동 평가](../evals/README.md)를 적용합니다. 대표 요청에 대한 절차 선택·수정 범위·검사 선택과 산출물을 확인합니다.
문법·링크 검사, 에이전트 실제 실행, 사람의 판정을 구분합니다. 실행 환경이 없으면 행동 평가를 통과로 기록하지 않습니다.

## 6. 완료 근거

프로젝트의 기록 위치에 다음 형식으로 남깁니다. 날짜와 상태는 실제 결과를 사용합니다.

```text
작업 범위:
변경 파일:
검증 환경과 버전 확인 위치:
실행 명령 또는 도구:
결과: 테스트 N개 통과 / 실패 N개 / 오류 N개 / 건너뜀 N개
문서·링크·그림의 확인 범위:
교육 검토·기술 검토의 수행 방식과 주요 결과:
실제 외부 호출: 실행 또는 미실행
미검증 범위·남은 문제:
```

명령을 시도한 것과 성공한 것은 다릅니다. 실행 오류나 승인·도구 오류가 있으면 실제 원인과 수행하지 못한 검사를 그대로 기록합니다.
