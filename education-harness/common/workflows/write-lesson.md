# 새 단원 작성

## 1. 범위 정하기

프로젝트 설정과 교육 계획을 확인하고 아래 내용을 먼저 짧게 정리합니다.

- 단원 ID, 제목, 선수 단원과 새 개념
- 수강생이 실행할 입력·기능·출력
- 문서·보충 문서·실행 코드·테스트의 위치
- 이번에 다루지 않는 선택 심화
- 기존 도구로 수행할 로컬 검증과 실제 외부 검증의 범위

## 2. 실행 코드와 테스트 구현

구현 수업은 최소 정상 흐름부터 실행 가능하게 만듭니다. 프로젝트의 기존 빌드·설정·테스트 방식을 사용합니다.
미래 단원의 코드를 import하거나 불필요한 공통 계층을 만들지 않습니다.
테스트는 주요 동작과 의미 있는 실패를 확인합니다. 보조 코드가 있으면 학습에서 직접 읽을 범위를 지정합니다.
실제 서비스 접속 테스트는 프로젝트의 로컬·Live 구분 방식을 따릅니다.

## 3. 설명 연결

[단원 템플릿](../templates/lesson.md)으로 작성합니다. 새 개념을 먼저 설명한 뒤 코드의 입력·처리·결과를 연결합니다.
긴 설명은 [보충 템플릿](../templates/supplement.md)으로 분리합니다.
실행 위치·설정·명령·예상 결과와 한 번 바꿔 볼 실험을 제공합니다.
자연어 응답이나 외부 서비스 결과의 예시는 실제 실행 결과와 구분합니다.
코드와 연결되는 설명을 작성한 뒤 학습자 입장에서 실행 안내를 순서대로 점검합니다.
비교 전 결과를 확보할 수 있는지, 재시작·재적재가 필요한지, 차이를 확인할 출력·기록이 있는지, 원복 방법이 있는지 확인합니다.
해당하지 않는 저장 정책 표나 실패 다이어그램을 모든 수업에 추가할 필요는 없습니다.

## 4. 검토와 검증

[검토 기준](../rules/review.md)으로 교육·기술 관점을 확인하고 [검증 절차](verify-materials.md)를 실행합니다.
검토 역할을 별도로 실행할 때는 [사용 안내의 역할 규칙](../../README.md)을 따릅니다.
실패하면 원인을 수정하고 해당 검사부터 재실행합니다. 새 문제가 없으면 불필요하게 전체 검사를 반복하지 않습니다.

## 5. 마무리

교육 계획·단원 대응·실습 README·필요한 실행 안내를 갱신하고 검증 근거를 기록합니다.
단원별로 실행 가능한 상태를 만든 뒤 커밋합니다. 실패·미검증 상태를 완료로 표시하지 않습니다.
검증이 막히면 가능한 독립 작업을 마치고 구체적인 원인과 남은 검사를 알립니다. 요청하지 않은 승인 절차를 새로 만들지 않습니다.
