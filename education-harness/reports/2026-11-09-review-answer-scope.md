## 최초 검토의 추가 개선 권장 사항

아래는 새로 발견한 개선 항목입니다. 줄 번호는 확인 질문 절의 검토 시점 위치입니다. 모두 오류라고 단정하는 목록은 아니며, 본문에서는 설명했지만 질문·해설만 읽으면 조건이 생략되는 경우를 포함합니다.

### 1. 단위가 다른 ‘호출 1회’를 구분 — 중간

위치: [00장](../../Spring-AI-Agent-Learning/docs/lessons/00-llm-and-spring-ai.md) 145행 4번, [메시지 보충](../../Spring-AI-Agent-Learning/docs/lessons/00-llm-and-spring-ai/01-prompt-and-messages.md) 354행 1번.

질문·해설은 메시지 두 개를 한 요청에 담으면 모델을 한 번 호출한다고 설명합니다. 메시지 개수만으로 HTTP 요청 횟수를 결정할 수는 없습니다. 이 페이지의 단순 예에서는 맞지만, 자동 도구 루프나 통신 재시도가 포함되면 `call()` 한 번에서 HTTP 요청이 여러 번 발생할 수 있습니다.

- 질문 개선: “도구 호출과 통신 재시도 없이 system 1개와 user 1개를 한 프롬프트로 한 번 전달하면 메시지 수와 모델 HTTP 요청 수는 각각 얼마인가요?”
- 해설 개선: “메시지는 2개, 모델 HTTP 요청은 1회입니다. 메시지 수만큼 모델을 호출하는 것은 아닙니다.”

단순 예의 조건을 한 문장으로 명시하면 충분하며, 입문 질문에 재시도 내부 구현까지 추가할 필요는 없습니다.

### 2. Evaluator의 반환 대상 표현 — 중간

위치: [12-2](../../Spring-AI-Agent-Learning/docs/lessons/12-evaluation/02-model-judge.md) 130행.

“Evaluator가 true를 반환하면”은 API 반환 타입을 부정확하게 줄인 표현입니다. 본문의 API는 `evaluate(...)`로 EvaluationResponse를 받고, `.isPass()`로 boolean을 읽습니다. 샘플 서비스가 반환하는 boolean과 구분해야 합니다.

- 질문 개선: “평가 결과의 `EvaluationResponse.isPass()`가 true이면 답변의 사실성이 보장되나요?”
- 해설 개선: “아닙니다. 평가 모델이 그 기준을 통과했다고 판정한 결과입니다. 근거와의 일치도 평가가 원문 자체의 진실성을 증명하지는 않으며, 다양한 반례와 사람 검토가 필요합니다.”

확인 근거: [AnswerEvaluator.java](../../Spring-AI-Agent-Learning/labs/12-02-model-evaluation/src/main/java/com/example/ailearning/l12judge/AnswerEvaluator.java)의 `.evaluate(request).isPass()`.

### 3. ‘쿠키가 다르다’의 대상 — 중간

위치: [07-5](../../Spring-AI-Agent-Learning/docs/lessons/07-chat-memory/05-isolation.md) 89행 5번.

현재 질문은 모든 쿠키 차이가 대화 격리를 만든다고 읽힐 수 있습니다. 이 예제에서 소유자를 구분하는 값은 서버의 HTTP 세션 ID입니다. 해설에는 서로 다른 세션 소유자라는 조건이 있으나 질문에서도 명확히 해야 합니다.

- 질문 개선: “서로 다른 HTTP 세션을 사용하는 두 방문자가 같은 conversationId를 보내도 대화가 섞이지 않는 이유는 무엇인가요?”
- 해설 개선: “서버가 얻은 세션 ID와 conversationId를 함께 메모리 키로 사용하므로 서로 다른 키로 저장·조회하기 때문입니다. 같은 세션을 공유하면 이 방식만으로 두 사람을 구분하지는 못합니다.”

확인 근거: [MemoryController.java](../../Spring-AI-Agent-Learning/labs/07-00-chat-memory/src/main/java/com/example/ailearning/l07memory/MemoryController.java)가 `session.getId()`를 서비스에 전달합니다.

### 4. 샘플 상태명을 묻는 질문이 남아 있음 — 중간

위치: [10-3](../../Spring-AI-Agent-Learning/docs/lessons/10-rag/03-evidence.md) 94행 3번.

`NO_CONTEXT`·`NO_ANSWER`는 샘플이 정의한 상태입니다. 해설의 개념은 유용하지만 질문은 상태명의 뜻을 외우게 하기보다 검색 단계와 생성 단계의 차이를 물어야 합니다.

- 질문 개선: “검색한 근거가 없는 경우와, 근거는 찾았지만 그 내용으로 답할 수 없는 경우를 RAG에서 왜 구분해야 하나요?”
- 해설 개선: “전자는 검색 결과가 없어 생성 호출 전에 답변을 보류할 수 있는 경우이고, 후자는 검색한 자료로 질문에 답할 수 있는지 생성 단계에서 판단하는 경우입니다. 검색 조건·문서 적재의 문제와 근거의 충분성·답변 가능성 문제를 나누어 확인할 수 있습니다.”

필요하면 본문에서만 각 개념이 샘플의 어느 상태에 대응하는지 연결하면 됩니다.

### 5. COUNT의 지표 이름과 태그 — 낮음

위치: [12-4](../../Spring-AI-Agent-Learning/docs/lessons/12-evaluation/04-actuator.md) 131행.

“토큰 COUNT”는 본문 표를 읽으면 이해할 수 있지만 질문에서 지표·태그가 생략됐습니다. 토큰의 input·output·total을 함께 더하면 중복 집계할 수 있다는 본문 설명도 있으므로 정확한 대상을 보여주는 편이 좋습니다.

- 질문 개선: “`gen_ai.client.token.usage`에서 `gen_ai.token.type=total`로 조회한 COUNT가 15이면 모델을 15번 호출했다는 뜻인가요?”
- 해설 개선: “아닙니다. 선택한 태그 범위의 누적 총 토큰 수가 15라는 뜻입니다. 모델 호출 수는 `gen_ai.client.operation`의 COUNT를 별도로 확인합니다.”

본문과 [ObservationLocalModelTest](../../Spring-AI-Agent-Learning/labs/12-04-observability/src/test/java/com/example/ailearning/l12observe/ObservationLocalModelTest.java)는 이미 이 지표·태그를 구분합니다. 수치 오류가 아니라 질문 대상의 명시 수준 문제입니다.

### 6. Advisor 실행 횟수의 전제 — 낮음

위치: [08-3](../../Spring-AI-Agent-Learning/docs/lessons/08-advisors/03-observe.md) 72행 4번.

해설은 현재 A/B 배치에서 도구 1회 후 최종 답변을 받는 예를 전제로 A 1쌍·B 2쌍을 설명합니다. 근거는 있으나 질문의 “도구를 한 번 호출했을 때”만으로는 계속되는 도구 요청이나 다른 Advisor 배치까지 구분되지 않습니다.

- 질문 개선: “현재처럼 A는 도구 루프 밖, B는 안에 두고 검색 도구를 1회 실행한 뒤 최종 답변을 받으면, 왜 A의 before·after는 각 1회이고 B는 각 2회인가요?”
- 해설 개선: “A는 전체 루프를 한 번 감쌉니다. B는 최초 질문과 도구 결과를 전달하는 두 모델 요청을 각각 감싸므로 두 번 실행됩니다.”

등록 위치와 실행 흐름이 바뀌어도 항상 같은 횟수라고 일반화하지 않도록 조건을 붙이는 개선입니다.

## 최초 검토의 하네스 적용 방안 — 후속 적용 완료

현재 [확인 질문 기준](../common/rules/authoring.md#확인-질문과-해설)은 대상 이름·값·단위와 학습 목적을 이미 다룹니다. 별도 긴 체크리스트를 만들기보다 기존 작성·검토 기준과 템플릿 안내에 아래 내용을 보완하는 방안을 권장합니다.

1. **해설 순서:** 결론 → 적용 대상과 범위 → 이유 순으로 답한다. 샘플 실행 횟수나 상태값은 개념 설명에 필요한 경우에만 근거와 함께 덧붙이며, 이를 일반적인 보장처럼 쓰지 않는다.
2. **횟수·시간의 조건:** 수치가 나오면 사용자 요청·ChatClient 실행·모델 HTTP 요청·도구 실행 중 무엇을 세는지와 누적 범위를 명시한다. 정확한 횟수를 묻는 경우 결과를 결정하는 도구 루프·재시도·최종 답변 등의 전제만 질문 가까이에 제시한다.
3. **같은 대상에 답하기:** 질문에서 특정한 API 반환값·메타데이터·설정 범위를 해설에서도 그대로 유지한다. 프레임워크 응답을 샘플 서비스의 응답이나 다른 계층의 횟수로 바꾸어 설명하지 않는다.

작성 규칙에는 위 원칙을 간결하게 추가하고, 검토 기준에는 “해설의 조건과 적용 범위가 질문과 일치하며, 샘플 수치를 일반화하지 않았는가?” 한 항목을 보완하면 됩니다. 두 템플릿에는 “수치를 묻는다면 세는 대상·범위·필요한 전제를 밝히고 해설은 결론과 이유로 작성한다”는 작성 안내를 추가하는 정도가 적절합니다. 새 필수 문항·새 테스트·새 템플릿 절은 필요하지 않습니다.
