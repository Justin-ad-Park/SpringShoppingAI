# 교육 설명 축약과 하네스 0.2.28 재검토

검토일: 2026-11-19.<br>
대상 독자는 Spring을 사용했지만 Spring AI는 처음인 개발자입니다.

## 결론

전체 작업 트리를 이전 커밋으로 되돌리기보다, 현재의 단계별 실습 구조를 보존하면서 과도하게 줄어든 교육 설명을 선택 복원하는 편이 적절합니다.<br>
하네스의 삭제 우선 표현도 보완해야 합니다.<br>
규칙 변경만으로 이미 누락된 설명이 복원되는 것은 아니므로 문서 복구를 별도로 수행해야 합니다.

09-2에는 이번 요청으로 필요한 설명을 복원했습니다.<br>
나머지 항목은 종합 검토와 복원 계획이며 아직 적용하지 않았습니다.<br>
커밋하지 않았습니다.

  해당 커밋의 교재 변경은 08장에 한정되어 있고, 09~13장의 구조 개편은 포함되지 않았습니다.

  문서 이동은 삭제로 단정하지 않고 10장의 새 파일과 13-8의 이동 내용을 확인했습니다.
- 09-2, 13-2, 13-4를 집중 검토하고, 설명 삭제가 큰 10-1, 12-1, 12-3, 12-5 및 연결 문서를 확인했습니다.<br>
  삭제량은 조사 순서를 정하는 용도로만 사용했고 품질 판정 기준으로 삼지 않았습니다.

- 실행 코드가 바뀌지 않은 다른 단원 전체를 처음부터 재평가한 검토는 아닙니다.<br>
  다른 대화창의 변경과 이번 작업의 변경을 구분해야 합니다.
- 현재 파일과 커밋은 삭제 결과와 포함 범위를 보여주지만, 각 대화에서 어떤 판단으로 삭제했는지까지 증명하지는 않습니다.

| 구분 | 확인한 문제 | 판단과 조치 |
|---|---|---|
| 하네스의 목적 | 이해·실행·결과 해석에 도움 없는 제작 이력과 조사 메모를 정리하려는 목적 | 유지할 가치가 있음 |
| 삭제를 유도하는 문구 | “필요성을 구체적으로 답하기 어려운 설명은 제거를 먼저 검토” | 필요성 판단이 불확실한 설명도 삭제 대상으로 기울어짐. 보존·재배치·축약·삭제 순으로 역할을 판단하도록 수정 제안 |
| 보호 기준의 편중 | 보존 예시는 동작 조건·비용·실패·검증 한계에 집중 | 개념 정의·사용 이유·입출력 예시·단계 연결·결과 읽는 방법도 교육의 핵심임을 명시할 필요 |
| 실제 적용 | 09-2의 용어와 비교 전제, 13-4의 관찰 기준이 사라짐 | 기존 규칙의 초보자 설명·삭제 시 조건 보존 원칙에도 어긋남. 하네스만의 문제로 설명할 수 없음 |
| 검증 방식 | 링크 검사와 diff 검사로 내용 선별의 적절성을 확인한 것처럼 받아들일 위험 | 기술적 연결 검사와 교육 품질 검토를 구분. 실제로 초보자가 입력→처리→결과를 설명할 수 있는지 확인 |
| 변경이 섞인 상태 | 구조 분리·파일 이동·설명 축약이 함께 진행됨 | 목표 밖으로 옮긴 설명과 완전히 사라진 설명을 구분하고 복구 대상을 결정 |

`499011a`의 08장 변경은 폐기 예정 이름·배포 여부 조사 설명 등을 줄인 것으로, 현재 실습의 개념 정의를 대량 제거한 변경은 아닙니다.<br>
그 커밋 전체를 되돌려야 한다는 근거는 부족합니다.<br>
반면 그 안의 삭제 우선 문구는 과도한 축약을 막기에 충분하지 않으므로 부분 보완이 적절합니다.<br>
독립 세션 행동 평가는 당시에도 실행하지 않았습니다.

직전 내용 정리에서 적용한 11개 항목은 9개 문서의 제작 이력·이동 이력·중복 설명 정리였습니다.<br>
이번 대조에서 그 변경 자체가 핵심 개념을 대량 제거한 사례는 확인하지 못했습니다.<br>
현재 09~13장의 설명 부족은 다른 미커밋 구조 개편과 함께 보이므로, 모든 삭제를 이 11개 항목이나 `499011a`의 직접 변경으로 묶어 평가하면 안 됩니다.

## “학습과 무관한 불필요한 정보”의 범위

불필요한 정보란, 대상 독자의 개념 이해·사용 이유·코드 흐름·실행·결과 해석에 기여하지 않고 현재 학습 목표나 연결된 후속 학습에서도 사용할 이유가 없는 정보입니다.<br>
단원 목표를 실행 API만으로 좁혀 개념 설명을 제거하지 않습니다.

| 처리 | 해당 내용 | 예 |
|---|---|---|
| 본문에 유지 | 개념과 새 용어, 왜 사용하는지, 누가 무엇을 처리하는지, 주요 입력·출력과 결과 해석 | score는 사실 확률이 아님, 의도 추출과 도구 선택은 다른 단계 |
| 해당 코드 옆에 유지 | 정상 이해·실행에 필요한 전제, 비용·저장·실패 영향 | 같은 모델·차원으로 비교, 재시작 시 재임베딩, 실패한 대화 미저장 |
| 다른 단계로 이동 | 현재 목표를 넘지만 후속 학습에서 실제 사용하는 설명 | 전체 요청 시간 제한 → 13-8. 이동한 설명으로 직접 연결 |
| 중복을 줄여 연결 | 앞 단원과 같지만 현재 예제를 읽을 때 다시 필요한 설명 | `.entity()`를 한 문장으로 복습하고 04장으로 연결 |
| 삭제 후보 | 현재 사용하지 않는 기능의 조사 내역, 제작 과정·편집 이력, 의미가 같은 반복 문장 | “이전에 여기에 있었지만 옮겼다”, 현재 실습과 무관한 폐기 API 목록 |
| 판단 유보 | 중요성을 아직 확인하지 못한 설명 | 사용처와 선수 지식을 먼저 확인. 불확실하다는 이유만으로 삭제하지 않음 |

부정문이라는 이유만으로 지우지 않습니다.<br>
“score는 사실 확률이 아니다”는 오해를 막는 핵심 설명입니다.<br>
전체 소스 링크가 있거나 다른 문서에 비슷한 설명이 있다는 사실만으로 현재 단계의 설명을 생략하지 않습니다.

## 전체 원복 대신 어떻게 작업할까?

1. 변경 전 HEAD와 현재 작업 트리의 추적·미추적 파일을 포함한 복구본을 확보하고, 이후 수정 파일을 기록합니다.<br>
   다른 대화창의 편집과 충돌할 파일은 수정 직전에 다시 읽습니다.
2. 문서별 삭제 내용을 ‘삭제 적절 / 새 위치에 존재 / 복원 필요 / 사실 확인 필요’로 분류합니다.<br>
   이동된 파일은 이름이 아니라 내용과 학습 역할로 대응시킵니다.
3. 하네스에는 위 정보 선별 기준을 원칙 소유 파일에 모아 부분 반영하고, 검토 기준에서는 그 원칙의 적용 여부를 확인합니다.<br>
   모든 문서에 형식적인 절·표를 추가하는 규칙은 만들지 않습니다.
4. 09-2→13-2→13-4를 먼저 복구하고, 이어 10·12장의 누락을 보강합니다.<br>
   전체 소스를 그대로 복구하는 대신 개념→입력 예시→단계별 코드→출력 해석으로 읽는 흐름을 만듭니다.<br>
   전체 실행 소스는 링크로 제공합니다.
5. 메서드·설정·응답 필드를 실제 코드와 대조합니다.<br>
   본문 복원에 예전 RunState 인자나 삭제된 trace를 잘못 되살리지 않습니다.<br>
   설명 수정만으로 끝나는 경우와 코드 수정이 필요한 경우를 구분합니다.
6. 내용 검토에서는 학습자가 “무슨 문제를 해결하는가 / 이 값이 무엇인가 / 다음 단계로 무엇이 전달되는가 / 결과가 왜 이렇게 나오는가”에 본문으로 답할 수 있는지 확인합니다.<br>
   링크·코드 발췌·명령도 별도 검사합니다.
7. 하네스 수정 시 행동 평가에는 ‘폐기 API 조사 설명 정리’와 ‘초보자용 용어·흐름·비용 설명 보존’을 함께 넣습니다.<br>
   삭제량이 적거나 문서가 짧아졌다는 이유로 통과 처리하지 않습니다.

전체 원복은 선택 복원으로 일관성을 회복하기 어렵다고 확인되었을 때만 검토합니다.<br>
그 경우에도 해당 문서의 설명 부분만 이전 버전에서 가져와 현재 코드에 맞추며, 저장소 전체의 git restore/reset으로 다른 작업을 없애지 않습니다.
