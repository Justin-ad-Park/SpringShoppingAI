# 학습용 Mock 서버 공통화 검토안

검토 당시 서버 코드를 읽어 정리한 설계안입니다. 이후 사용자의 구현 요청에 따라 적용을 마쳤습니다. 실제 API는 [공통 도구 안내](../../Spring-AI-Agent-Learning/test-support/README.md), 검증 결과는 [검증 기록](../../Spring-AI-Agent-Learning/docs/verification.md)을 참고합니다.

## 확인한 중복

14개 실습 모듈에 서버 구현이 반복됩니다. 13개 서버 클래스와 첫 호출 테스트 내부의 HTTP 서버가 있습니다.
패키지·클래스 이름을 제외하면 다음 구현은 각각 동일합니다.

| 단원 | 같은 구현 또는 주요 차이 |
|---|---|
| 04·07 | 동일한 채팅 응답 서버 |
| 05·06 | 동일한 채팅·도구 호출 응답 서버 |
| 10 표준 RAG·11 평가 | 동일한 채팅·임베딩·오류·지연 응답 서버 |
| 11 모델 평가·11 관측 | 동일한 채팅 응답·usage 서버 |
| 02 다중 모델 | OpenAI·Anthropic의 서로 다른 응답 형식과 인증 헤더 기록 |
| 08 | 채팅·도구 호출 외에 HTTP 오류 상태 설정 |
| 09 | 문자열·배열 입력에 대한 임베딩 응답 |
| 10 직접 RAG·12 통합 | 채팅·임베딩을 결합하며 12는 도구 호출도 처리 |

공통으로 추출할 부분은 서버 시작·종료, 임의 포트 배정, HTTP 입출력, 요청 기록, 제공 업체 응답 형식 생성입니다.
단원별로 남길 부분은 고정 응답 내용, 도구 이름·인자·순서, 요청에 따른 분기, 임베딩 값, 실패·지연 시나리오입니다.

## 권장 구조

테스트 전용 `Spring-AI-Agent-Learning/test-support` 모듈을 추가하고, 실습은 `testImplementation`으로만 사용합니다.
애플리케이션의 Service·Controller·설정과 Live 테스트의 실제 모델 연결은 바꾸지 않습니다.

```text
test-support/
  src/main/java/com/example/ailearning/testsupport/
    StubHttpServer.java       HTTP 처리·포트·요청 기록·자원 정리
    OpenAiStubServer.java     채팅·도구 호출·임베딩 응답 형식
    AnthropicStubServer.java  Anthropic 응답 형식
    TestOutput.java           케이스 이름과 실제 결과 출력
```

HTTP 공통 구현은 내부에서 사용하고, 학습자가 읽는 테스트에는 OpenAiStubServer와 시나리오만 보이게 합니다.
제공 업체의 서로 다른 규격까지 하나의 조건문이 많은 서버로 합치지는 않습니다.
다중 제공 업체 테스트는 두 서버를 각각 만들고 주소도 따로 주입합니다.

루트 build.gradle은 현재 모든 말단 프로젝트를 Spring Boot 애플리케이션으로 취급합니다.
새 test-support는 이 대상에서 제외하고 일반 Java 라이브러리로 구성해야 합니다. 필요한 JSON 의존성만 사용하고, 기존 버전 관리와 연결합니다.

## 테스트에서 읽을 모습

아래는 검토 당시의 API 예시입니다. 구현된 사용법과 초기화 범위는 위 공통 도구 안내를 기준으로 합니다.
`text(...)`는 assistant의 content를 만들고, 제공 업체의 HTTP 응답 포장은 공통 서버가 담당합니다.

```java
// 문자열 응답
MODEL.respondWith(text("안녕하세요."));

// record 변환에 사용할 JSON도 assistant의 content로 전달
MODEL.respondWith(text("""
        {"category":"음료","maxPrice":15000}
        """));

// 도구 요청 → 결과를 받은 뒤 최종 응답
MODEL.respondInOrder(
        toolCall("search-1", "searchProducts", "{\"category\":\"음료\"}"),
        text("허브티 12000원입니다."));
```

상태에 따라 달라지는 06·12의 시나리오는 `respondUsing(request -> ...)` 같은 콜백으로 테스트 파일에 둡니다.
상품 ID·가격·정책·상태를 공통 서버가 추측하거나 자동 판단하지 않습니다.
임베딩도 `embeddingUsing(text -> ...)`로 벡터를 지정하며, 단원별 검색용 데이터는 각 실습에 둡니다.
오류 상태·지연·usage·요청 기록 조회는 필요한 테스트에서만 명시합니다.

## 작업 순서

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 공통 HTTP 서버와 OpenAI 텍스트 응답부터 구현, 04 적용 | record 변환·누락·형식 오류·값 오류·공백 입력의 기존 5개 테스트 통과 |
| 2 | 02 첫 호출·07·11 모델 평가·관측 적용, Anthropic 형식 분리 | 인증 헤더·모델 선택·대화 전달·usage 검증 유지 |
| 3 | 순차 응답·콜백으로 05·06·08의 도구 시나리오 적용 | 도구 인자·호출 횟수·Advisor 순서·실패 후 저장 정책 유지 |
| 4 | 임베딩 응답과 오류·지연 설정을 추가해 09·10·11·12 적용 | 검색 점수·필터·출처 검증·429·타임아웃·상한 검증 유지 |
| 5 | 결과 출력 도구와 문서의 테스트 읽기 안내 정리, 이전 서버 제거 | 모든 로컬 케이스에 이름과 결과 출력, 단원별 중복 서버 없음 |

단계마다 해당 단원의 로컬 클래스만 실행하고 빌드한 뒤 커밋합니다. 마지막에 전체 로컬 71개를 다시 확인합니다.
Live 클래스도 컴파일하되 공통 Mock 서버를 참조하지 않는지 확인합니다.

## 기존 동작을 보존할 지점

- 기록 초기화와 응답 시나리오 초기화를 구분합니다. 서버 시작 시 임베딩한 기록을 지워 기존 검증 근거가 사라지지 않게 합니다.
- 실패한 HTTP 요청도 횟수에 포함하며, 순차 응답이 소진되면 예측 가능한 오류로 드러냅니다. 무조건 성공 응답으로 덮지 않습니다.
- 지연 중인 요청이 다음 테스트의 응답 설정을 읽지 않게 요청별 시나리오를 고정합니다. 종료 시 실행 작업과 소켓도 정리합니다.
- 각 테스트 클래스가 자기 서버·포트·기록을 소유합니다. 전역 서버 하나를 공유하지 않습니다.
- 도구 호출 ID·usage·입력 배열·인증 헤더처럼 현재 검증하는 필드를 유지합니다. 키와 인증 헤더는 결과 출력에서 제외합니다.
- 한글 테스트명·결과 출력·assertion·로컬/Live 클래스 구분은 유지합니다. 기존 테스트를 없애 코드 줄 수만 줄이지 않습니다.

권장 시작점은 04입니다. 공통화 후 이 테스트에서 학습자가 읽을 것은 입력 질문·약속한 모델 응답·실제 결과·assertion이어야 합니다.
