# 처음 배우는 개발자를 위한 학습 방법

이 교재는 Spring으로 Controller와 Service를 작성할 수 있지만, AI 모델은 처음 사용하는 개발자를 대상으로 합니다.
Spring Academy의 **배경 개념 → Spring AI 구현 → 실습** 구성을 참고하되, 한 수업의 입력·처리·결과를 더 작게 나눕니다.
공식 강의의 본문이나 코드를 번역한 자료가 아니라, 이 저장소의 쇼핑 예제를 설명하는 자체 교재입니다.

## 한 번에 어디까지 읽을까요?

00~04는 각 교재의 절을 순서대로 읽습니다. 05~13은 각 단원의 목차에서 소수업으로 들어갑니다.
한 번에 전체 애플리케이션을 작성하는 과정이 아닙니다.

| 단계 | 할 일 | 이번에 끝났다는 기준 |
|---|---|---|
| 개념 | 어떤 불편을 해결하는지 먼저 읽기 | 새 API 이름 없이 문제를 설명할 수 있음 |
| 코드 | 본문이 지정한 메서드 한두 개만 읽기 | 입력·호출 대상·반환값을 찾을 수 있음 |
| 실행 | 그대로 실행해 정상 결과 관찰 | 기대한 자료가 다음 단계에 전달됨을 확인 |
| 작은 변경 | 질문이나 옵션 하나만 바꾸기 | 변경 전후의 차이를 설명할 수 있음 |
| 보충 | 실패 처리·동시성·테스트 보조 코드 읽기 | 기본 흐름을 이해한 뒤 필요할 때 찾아봄 |

## 코드에서 먼저 찾을 세 가지

예를 들어 첫 실습의 `ChatService.ask(message)`는 다음처럼 읽습니다.

```text
입력: Controller가 받은 질문 message
처리: user(message)로 현재 사용자 메시지를 넣고 모델에 요청
결과: content()가 반환한 답변 문자열
```

- `prompt()`는 요청 조립 시작입니다. 이 줄만 실행했다고 외부 모델을 호출한 것은 아닙니다.
- `user(message)`는 질문을 프롬프트에 넣습니다. 프롬프트는 역할을 가진 메시지들의 묶음입니다.
- `call().content()`는 이 동기 호출 흐름을 실행해 답변 텍스트를 받습니다.
- 다음 단원에서는 문자열 대신 record, 메시지 한 개 대신 이전 대화, 고정 문자열 대신 검색 근거를 추가합니다.

새 문법이 나오면 AI 개념과 구분하세요. `record`는 Java 데이터 묶음이고, `.entity(...)`는 모델 응답을 그 타입으로 변환하는 Spring AI 기능입니다.

## Java 문법과 AI 기능을 구분하기

| 코드 모양 | 먼저 이해할 의미 |
|---|---|
| `record` | 값들을 묶은 Java 데이터 타입. AI 전용 문법 아님 |
| `var result = ...` | 오른쪽 값으로 지역 변수의 타입을 추론. 어떤 객체가 반환되는지 먼저 확인 |
| `List.of(...)` | 여러 값을 순서 있는 목록으로 묶음 |
| `item -> ...` | 각 값에 적용할 동작을 전달하는 람다 표현식 |
| `stream().map(...)` | 목록의 각 값을 다른 값으로 바꾸는 Java 처리 |
| `filter(...)` | 조건을 만족하는 값만 남김. 모델이 판단하는 필터와 구분 |
| `.entity(SomeRecord.class)` | 모델 응답을 해당 Java 타입으로 변환하는 Spring AI 기능 |

코드의 모든 줄을 AI 기능이라고 생각하지 말고, 일반 Java 처리와 모델을 호출하는 부분을 표시해 보세요.

## 무엇을 직접 작성해야 하나요?

| 코드 | 첫 학습에서 할 일 |
|---|---|
| Service의 프롬프트·도구 등록·검색 호출 | 직접 읽고 한 줄씩 설명 |
| Controller·입력 검증 | 익숙한 Spring 연결로 확인 |
| Executor·Future | 06의 기본 비교 뒤 [06-4](lessons/06-workflow-agent/04-future.md)에서 작업 제출·대기·취소 이해 |
| `support/RunState`, `CountedChatModel` | 제공된 보조 코드. [06-5](lessons/06-workflow-agent/05-limits.md)에서 호출 상한과 기록 연결 |
| `test-support`의 Mock 서버·결과 출력 | 공통 검증 도구. 단원에서는 지정한 응답·실제 결과·assertion부터 읽기 |
| 통합 단원의 여러 도구·메모리 조합 | 각 기능을 따로 실행한 뒤 책임 지도로 확인 |

보조 코드가 없는 것처럼 기능을 설명하지는 않습니다. 실행 제한·격리 등의 실제 동작과 한계는 보충 수업에 남깁니다.
처음부터 모든 클래스를 위에서 아래로 읽는 대신, 핵심 흐름을 이해한 뒤 호출되는 보조 코드로 확장합니다.

설정 이름과 루트 `.env` 작성 방법은 [실행 설정 안내](run-guide.md)에 모았습니다.

공통 도구의 API와 초기화 범위는 [test-support 안내](../test-support/README.md)에서 확인합니다.

## 테스트와 실제 모델 관찰은 다릅니다

Mock 테스트는 프롬프트 구성·도구 실행·값 검증 같은 Java 코드의 연결을 확인합니다.
고정 응답으로 통과했다고 모델이 한국어를 이해하거나 적절한 도구를 선택한다고 결론 내리지 않습니다.
실제 모델 실습에서는 답변·도구 선택·근거 사용을 따로 관찰합니다.

첫 실습은 단순한 두 클래스입니다. `FirstChatLocalModelTest`는 MockServer,
`FirstChatOpenAiLiveTest`는 실제 OpenAI에 접속합니다. IntelliJ에서는 원하는 클래스의 Run을 누릅니다.
첫 모듈의 전체 test에는 두 클래스가 포함됩니다. Mock만 원하면 클래스 필터를 사용합니다.
태그·실행 허용 변수·별도 Live 태스크를 도입하지 않습니다.

모든 학습 모듈의 실제 실행은 루트 `.env`를 읽습니다. 채팅은 `OPENAI_API_KEY`, `OPENAI_MODEL`을 사용하고,
임베딩을 사용하는 실습만 `OPENAI_EMBEDDING_MODEL`을 추가로 사용합니다.
09 검색 실습은 임베딩만 사용하므로 채팅 모델이 필요 없습니다.
두 업체를 사용하는 선택 실습은 Anthropic 설정도 필요합니다. 전체 대응은 [실행 설정 안내](run-guide.md)를 참고하세요.
`02-multiple-models`에도 별도 `MultipleProvidersLiveTest`가 있으며 실제 OpenAI·Anthropic을 호출합니다.
각 모듈의 전체 test에는 Live 클래스가 포함되므로, 로컬 테스트만 원하면 클래스 필터를 사용합니다.
이 두 Live 클래스를 제외한 자동 테스트는 파일 읽기를 끄고 로컬 고정 모델 서버를 사용합니다.

## 그림을 읽는 순서

[다이어그램 기준](diagram-guide.md)을 전체 수업에 적용합니다.
클래스 그림은 **책임**, 시퀀스 그림은 **한 요청의 시간 순서**, 흐름 그림은 **결정 주체**를 봅니다.
그림을 다 읽은 뒤 코드를 보는 것이 아니라, 그림의 호출 하나와 코드의 메서드 하나를 대응시키세요.
