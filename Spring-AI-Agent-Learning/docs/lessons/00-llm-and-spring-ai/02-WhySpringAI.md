# 기존 Spring 쇼핑몰의 AI 에이전트에 Spring AI를 선택한 이유

**기존 Spring 쇼핑몰에 AI 쇼핑 에이전트 챗봇을 추가하는 첫 선택으로 Spring AI를 권장합니다.**
상품·재고·주문·회원·배송 기능을 이미 Spring 서비스로 운영하고 있고, 팀이 Java와 Spring 운영에 익숙하다는 전제입니다.
쇼핑 에이전트의 핵심은 자연어 답변뿐 아니라 기존 업무 기능을 올바른 사용자 권한으로 호출하고, 그 결과를 근거로 응답하는 데 있습니다.
이 조건에서는 기존 서비스와 운영 체계를 재사용할 수 있다는 점이 선택의 주된 이유입니다.

이 문서는 기술 선택 이유와 권장 구성을 설명합니다. 아래 내용은 도입 제안이며, 모든 기능이 이미 구현된 것은 아닙니다.
확인 기준일은 **2026-11-12**이며, Spring AI 설명은 저장소의 [build.gradle](../../../../build.gradle)에 선언된 2.0.2를 기준으로 합니다.
프레임워크 전반의 비교는 [Spring AI와 LangChain](01-SpringAIvsLangChain.md)을 참고하세요.

## 1. Spring AI가 이 프로젝트에 적합한 이유

### 기존 서비스 로직을 도구로 재사용할 수 있다

상품 조회·장바구니·주문 조회 기능을 AI 전용으로 다시 구현하기보다, 필요한 기능만 호출하는 Java 도구를 만듭니다.
도구 메서드에 `@Tool`을 선언하고 `ChatClient`에 등록하면 모델이 해당 도구의 호출을 요청할 수 있습니다.
모델이 기존 서비스를 직접 실행하는 것이 아니라, 애플리케이션이 요청을 받아 인자를 검사하고 서비스를 실행합니다.
[Spring AI 도구 호출](https://docs.spring.io/spring-ai/reference/api/tools.html)

같은 애플리케이션 안의 Spring Bean이라면 Java 메서드 호출로 연결할 수 있으므로, AI 도구를 위해 HTTP API를 반드시 추가할 필요는 없습니다.
기존 기능이 다른 서비스에 있다면 해당 API나 MCP 연결을 사용합니다.
기존 서비스 전체를 그대로 도구로 공개하기보다, 입력·출력과 실행 범위를 제한하는 얇은 도구 계층을 두는 편이 적절합니다.

### 기존 인증·권한 체계에 연결하기 쉽다

Spring Security의 로그인 사용자 정보와 기존 권한 검사를 활용할 수 있습니다.
예를 들어 “내 주문 내역” 요청에서는 서버가 확인한 사용자 ID를 기준으로 조회하고, 모델이 보낸 사용자 ID를 신뢰하지 않습니다.
주문 ID를 인자로 받더라도 그 주문의 소유자가 현재 사용자인지 서비스에서 검사해야 합니다.

Spring AI를 추가했다고 이 검사가 자동으로 완성되는 것은 아닙니다.
비동기 실행·스트리밍·별도 서비스 경계에서는 인증 정보의 전달과 검증을 명시적으로 설계해야 합니다.
특히 Servlet 환경의 `SecurityContext`는 일반적으로 스레드에 연결되므로 새 스레드에서도 그대로 유지된다고 가정하면 안 됩니다.
[Spring Security 동시 실행 지원](https://docs.spring.io/spring-security/reference/servlet/integrations/concurrency.html)

### 팀의 기존 운영 체계와 Java 역량을 활용한다

Spring Boot 배포·설정·로깅·장애 대응 경험을 활용하고, Actuator·Micrometer 기반 관측 체계에 모델 호출 지표를 연결할 수 있습니다.
새로운 Python 실행 환경과 별도 AI 서비스의 배포를 초기 필수 조건으로 만들지 않아도 됩니다.
다만 모델 호출의 지연·비용·실패, 도구 반복 실행은 기존 API와 다른 특성이 있으므로 관측과 제한을 추가해야 합니다.
[Spring AI 관측성](https://docs.spring.io/spring-ai/reference/observability/index.html)

### 쇼핑 에이전트에 필요한 기본 구성요소를 제공한다

| 구성요소 | 이 프로젝트에서 맡길 역할 |
|---|---|
| ChatClient | 질문·지침·도구·응답 형식을 구성하고 모델 호출 |
| Tool Calling | 상품·재고·주문 등 기존 서비스 기능 연결 |
| Chat Memory | 이전 메시지 중 필요한 내용을 다음 모델 입력에 포함 |
| RAG Advisor | 관련 FAQ·정책 문서를 검색해 모델 입력에 포함 |
| 구조화된 출력 | 응답을 Java 객체 등으로 변환해 UI용 데이터 구성 |
| MCP | 원격 도구·자료 서버와 연결하거나 Spring 기능을 도구 서버로 제공 |

이 기능들은 Spring AI에서 제공하지만 필요한 의존성·저장소·Advisor·도구를 선택하고 구성해야 합니다.
[Spring AI 기능 개요](https://docs.spring.io/spring-ai/reference/)

### 모델 교체 시 애플리케이션 변경을 줄인다

공통 모델 API를 사용하면 OpenAI, Anthropic의 Claude, Google의 Gemini 등으로 연결을 바꿀 때 호출부 변경을 줄일 수 있습니다.
그러나 API 키·모델 이름만 바꾸면 언제나 동일하게 동작하는 것은 아닙니다.
제공 업체별 Starter·설정·도구 호출 지원·구조화 출력·토큰 제한을 확인하고, 같은 질문과 도구로 품질·비용·지연을 다시 평가해야 합니다.
[ChatClient와 모델 연결](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

## 2. 어떻게 연결해서 사용할까?

사용자가 채팅으로 요청하면 Spring 챗봇이 AI와 기존 쇼핑몰 기능을 연결합니다.
AI는 질문을 해석하고 답변을 만들며, 상품·주문 정보는 쇼핑몰 시스템이 조회합니다.

```text
[웹/앱 채팅 화면]
        ↕ 질문과 답변
[Spring 챗봇: 사용자 권한 확인·요청 처리·답변 검증]
    ├─ AI 모델: 질문 해석과 답변 작성
    ├─ 기존 쇼핑몰: 상품·재고·가격·혜택·장바구니·주문·배송 처리
    ├─ 문서 검색: FAQ·이용약관·교환/반품·배송 정책·상품 설명 확인
    ├─ 대화 기록: 이전 질문을 참고해 후속 질문 이해
    └─ 운영 점검: 응답 시간·비용·오류·답변 품질 확인
```

답변을 한꺼번에 보여주거나 생성되는 대로 조금씩 보여줄 수 있습니다.
조금씩 전달하는 방식을 스트리밍이라고 하며, SSE(Server-Sent Events)나 WebSocket 같은 통신 기술을 사용할 수 있습니다.
채팅 화면은 별도로 개발해야 하며, AI에 전달하는 지침만으로 사용자 권한이나 구매 확인 절차가 강제되지는 않습니다.

### 정보에 맞는 조회 방법을 선택한다

| 사용자의 요청 | 권장 처리 |
|---|---|
| “가벼운 운동화를 찾아줘” | 기존 상품 검색을 활용합니다. 단어와 의미를 함께 검색하는 기능이 있다면 그대로 사용하고, 부족한 부분만 개선합니다. AI 때문에 상품 검색용 저장소를 따로 만들 필요는 없습니다. |
| “반품은 언제까지 가능한가요?” | 관련 규정 문서를 찾아 AI가 참고하도록 합니다. 이를 RAG(Retrieval-Augmented Generation, 검색 증강 생성)라고 합니다. 정책뿐 아니라 상품 설명에도 사용할 수 있습니다. |
| “지금 가격과 재고를 알려줘” | 쇼핑몰 시스템에서 현재 값을 조회합니다. 오래된 문서의 가격·재고를 현재 정보처럼 안내하지 않습니다. 개인별 혜택과 배송 상태도 같은 원칙을 적용합니다. |

문서 답변은 최신 규정인지, 해당 상품·사용자에게 적용되는 내용인지 확인해야 합니다.
[Spring AI RAG 설명](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

### 답변은 글과 상품 카드로 보여준다

설명은 문장으로, 상품은 가격·재고·버튼이 있는 카드로 보여줄 수 있습니다.
화면에 쓸 정보를 정해진 항목으로 전달하는 것이 ‘구조화된 출력’입니다.
상품 정보와 버튼 동작은 서버가 확인한 값만 사용하며, AI가 만들어낸 상품 번호나 링크를 그대로 사용하지 않습니다.
글은 먼저 보여주더라도 상품 카드는 정보 검증이 끝난 뒤 전달하도록 정할 수 있습니다.

### 이전 대화는 필요한 만큼만 보관한다

“그중 더 저렴한 것은?” 같은 후속 질문을 이해하려면 앞선 대화를 다시 참고해야 합니다.
이를 돕는 기능이 Chat Memory이며, 모든 대화를 영구 보관하는 기능과는 다릅니다.
대화는 사용자별로 분리하고 보관 기간을 정합니다. 기본 설정에서는 서버를 다시 시작하면 기록이 사라질 수 있어 운영용 저장 방식을 따로 선택해야 합니다.
Redis 같은 저장소를 쓰려면 연결 방법도 확인해야 합니다. [대화 메모리 설명](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)

## 3. 쇼핑 에이전트에서 반드시 설계할 것

| 항목 | 권장 설계 |
|---|---|
| 쓰기 작업의 확인 | 장바구니 추가·주문 생성은 대상·수량·조건을 보여주고 사용자가 확인한 뒤 실행합니다. 확인한 작업과 실제 요청을 서버에서 연결하고, 재시도로 중복 실행되지 않게 합니다. 결제는 기존 결제 화면과 인증·승인 절차로 넘기는 것을 기본으로 합니다. |
| 사실에 근거한 응답 | 가격·재고·혜택은 도구 조회 결과를 근거로 답하도록 지침을 주고 서버에서도 검증합니다. 조회 실패나 정보 부족을 임의의 값으로 채우지 않습니다. 이 방식은 환각 위험을 줄이며 완전한 제거를 보장하지는 않습니다. |
| 권한 범위 제한 | 현재 로그인 사용자에게 허용된 도구와 데이터만 사용합니다. 모델이 선택한 주문 ID나 대화 ID도 소유권을 확인합니다. 조회·변경 권한은 실제 서비스 실행 지점에서 강제합니다. |
| 개인정보 보호 | 모델에 보낼 필드를 최소화하고 필요하면 마스킹합니다. 배송 조회에 필요하지 않은 주소·전화번호 등을 보내지 않으며, 메모리·로그·트레이스의 보관 범위도 정합니다. |
| 비용·지연 관리 | 단순 질의에는 작은 모델, 복잡한 판단에는 큰 모델을 사용하는 분기를 평가합니다. 모델별 품질 기준, 토큰·도구 호출 상한, 타임아웃·재시도 정책을 함께 둡니다. 스트리밍은 첫 응답 체감을 개선하지만 전체 처리 시간이나 비용을 반드시 줄이는 것은 아닙니다. |
| 평가·모니터링 | 대표 질문으로 답변 근거·상품 정확성·권한·쓰기 확인·도구 실패를 회귀 검증합니다. 운영에서는 도구 이름·성공/실패·지연·요청 추적 정보를 기록하고, 민감한 요청·응답 원문은 무조건 저장하지 않습니다. |

Spring AI에는 관측성과 평가 기능이 있지만 LangSmith 같은 독립적인 관리 플랫폼 전체를 내장하는 것은 아닙니다.
기존 지표·트레이싱 도구를 사용하거나, 필요하면 Langfuse 같은 오픈소스 플랫폼과 연동할 수 있습니다.
Langfuse는 Spring AI와 OpenTelemetry를 통한 연결 안내를 제공합니다. 이는 연동 선택지이며 실제 사용 빈도를 뜻하지 않습니다.
참고 예제의 Spring AI·Boot 버전과 의존성이 현재 프로젝트에 맞는지 확인해야 합니다.
[Spring AI 관측성](https://docs.spring.io/spring-ai/reference/observability/index.html), [Langfuse 연동 안내](https://langfuse.com/integrations/frameworks/spring-ai)

## 4. LangGraph를 추가로 고려하는 시점

다음 요구가 실제로 커지면 LangGraph 등 별도 오케스트레이션 도구를 검토합니다.

- 여러 에이전트의 협력, 복잡한 분기·루프·재시도, 상태 저장과 중단 후 재개가 필요할 때
- 추천·개인화·랭킹 등 Python 기반 ML 로직과 에이전트를 긴밀하게 결합해야 할 때
- 기존 Java 연동만으로는 실험하기 어려운 기법이나 Python 도구를 빠르게 비교해야 할 때

LangGraph는 LangChain과 함께 사용할 수 있는 별도 프레임워크이며, 단일 에이전트와 고정 Workflow에도 사용할 수 있습니다.
분기·반복·재시도가 있다는 이유만으로 바로 도입하는 것은 아닙니다. 단순 흐름은 Java 코드와 Spring AI의 도구 호출 기능으로도 구성할 수 있습니다.
[LangGraph 개요](https://docs.langchain.com/oss/python/langgraph/overview)

Python 라이브러리가 핵심이라면 기존 Spring 업무 서비스는 유지하고 Python 에이전트 서비스를 API로 호출하는 구성을 검토합니다.
이때도 상품·주문 권한과 변경 작업의 최종 책임은 해당 업무 서비스가 유지해야 합니다.
LangGraph 자체는 JS/TS도 지원하므로 별도 Python 서비스가 모든 경우의 필수 조건은 아닙니다.

서비스가 늘어나면 배포·인증 정보 전달·타임아웃·실패 복구·분산 추적·API 버전 관리도 늘어납니다.
따라서 현재 전제에서는 기존 Spring 애플리케이션에 챗봇 기능을 추가하는 구조로 시작하고,
흐름의 복잡도·팀 경계·배포 요구가 분리 비용을 정당화할 때 별도 AI 서비스를 검토하는 편이 현실적입니다.

## 5. 어떤 순서로 도입할까?

| 단계 | 제공할 기능 | 확인할 것 |
|---|---|---|
| 1. 조회 중심 | 상품 찾기·상세 안내·FAQ 답변 | 정보가 정확한지, 모를 때 모른다고 답하는지, 비용과 응답 시간이 적절한지 처음부터 평가합니다. |
| 2. 개인별 기능 | 내 주문·배송 조회·확인 후 장바구니 담기 | 본인 정보만 보이는지, 확인한 작업만 한 번 실행되는지 검사합니다. 가격·재고는 실행 직전에 다시 확인합니다. |
| 3. 상담 개선 | 개인화 추천·앞선 대화를 이어가는 상담 | 개인정보 사용 범위와 추천·대화 품질을 확인하고, AI 모델을 바꿔도 기존 기능이 잘 동작하는지 평가를 강화합니다. |
| 필요 시 확장 | 복잡한 AI 처리 기능을 별도 서비스로 분리 | 얻는 효과가 추가 개발·배포·운영 부담보다 큰지 비교합니다. |

선택의 기준은 프레임워크 이름보다 **기존 업무 기능의 재사용, 권한과 변경 작업의 통제, 관찰 가능한 품질과 운영 비용**입니다.
이 프로젝트에서는 그 조건을 기존 Spring 기술 안에서 먼저 충족하기 위해 Spring AI를 중심으로 시작합니다.
