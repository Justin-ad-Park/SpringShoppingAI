# 11-7. 원격 도구의 권한과 실패 처리

## 이번 수업의 목표

11-1~6 이후의 선택 보충입니다. 로컬 실습을 원격 서비스로 확장할 때 도구 발견·실행·업무 성공을 구분하고 권한·재시도 기준을 설명합니다. 새로운 서버나 인증 코드를 구현하는 수업은 아닙니다.

## 1. 도구를 발견한 것과 실행 가능한 것은 다르다

| 단계 | 확인한 것 | 아직 확인하지 않은 것 |
|---|---|---|
| 연결·도구 목록 조회 | 서버와 통신하고 정의를 읽음 | 현재 사용자의 주문 조회 권한 |
| 도구 호출 응답 수신 | 원격 응답을 받음 | 업무 성공과 응답 내용의 타당성 |
| 업무 결과 검증 | 필요한 조회·계산 조건 통과 | 주문 확정 같은 다른 업무의 완료 |

이 샘플의 `ShoppingMcpGateway.parseToolResult()`는 JSON 텍스트 블록 하나를 읽는 자체 계약입니다. MCP 결과의 모든 형태를 처리하는 범용 파서가 아닙니다. 다른 서버를 연결할 때 content 형식·오류 표현·도구 이름 충돌을 확인해야 합니다.

MCP는 tools 외에 resources·prompts 등의 기능도 다룹니다. 이번 수업은 상품 도구에 집중하며 전체 프로토콜 기능을 구현하는 실습은 아닙니다. [MCP Architecture](https://modelcontextprotocol.io/docs/learn/architecture)의 역할 구분을 참고합니다.

## 2. 고객 권한은 누가 확인할까?

“내 주문 배송지를 바꿔줘”를 확장한다고 가정하면, 모델이 올바른 주문 ID를 선택했어도 해당 고객의 주문인지 서버가 확인해야 합니다. 모델이 준 사용자 ID나 도구 설명만으로 권한을 부여하지 않습니다.

호스트는 업무에 필요한 도구만 모델에게 제공하고, 서버는 인증된 사용자·클라이언트가 해당 작업을 수행해도 되는지 검사합니다. 조회 도구와 상태를 변경하는 도구를 구분하며, 변경 작업에는 확인할 입력·승인·실행 결과가 필요합니다.

인증 정보의 전달·검증은 [MCP Security Best Practices](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)와 사용하는 Spring AI 보안 지원을 확인합니다. 여기서는 원칙만 다루며 현재 실습에 OAuth나 운영 인증이 구현됐다고 설명하지 않습니다.

## 3. 시간 초과 뒤 무조건 다시 실행해도 될까?

**멱등성**은 같은 작업을 반복해도 업무 결과가 중복해서 바뀌지 않는 성질입니다. 조회와 결제는 재시도 기준이 다릅니다.

| 상황 | 먼저 판단할 것 |
|---|---|
| 상품 조회 연결 실패 | 재시도할 오류인지, 전체 시간과 시도 수가 남았는지 |
| 주문 변경 뒤 응답만 유실 | 서버에서 변경이 이미 완료됐을 가능성 |
| 같은 요청 재전송 | 요청 ID로 이전 처리 결과를 조회·재사용할 수 있는지 |

응답을 못 받았다고 서버가 실행하지 않았다는 뜻은 아닙니다. 변경 도구는 요청 ID 기반 중복 방지나 처리 결과 조회가 필요할 수 있습니다. 이번 `quoteCart`는 계산만 하고 장바구니를 바꾸지 않습니다. 계산 예제의 재실행을 실제 구매 실행의 안전성 근거로 확대하지 않습니다.

`spring.ai.mcp.client.request-timeout`은 MCP 요청 한 번의 대기 범위입니다. 여러 모델 요청과 도구 호출을 합친 전체 사용자 요청 제한은 별도 정책이며, 기본 실습이 이를 모두 제공하지는 않습니다.

## 확인 질문

1. 모델에 주문 조회 도구를 제공했다면 현재 사용자의 주문인지 확인할 책임도 모델에 있나요?
2. 원격 변경 호출이 시간 초과되면 서버가 실행하지 않았다고 확정할 수 있나요?
3. 서버 한 곳의 JSON 결과를 읽는 코드가 있다면 모든 MCP 서버 결과를 처리할 수 있나요?

<details>
<summary>해설</summary>

1. 아닙니다. 서버와 애플리케이션이 인증된 사용자와 업무 대상의 권한을 검증해야 합니다.
2. 아닙니다. 실행 후 응답만 유실됐을 수 있습니다. 재시도 전에 중복 방지와 결과 확인 방법을 정해야 합니다.
3. 아닙니다. 서버의 반환 형식·오류·콘텐츠 블록과 도구 계약을 확인하고 연결 테스트를 해야 합니다.
