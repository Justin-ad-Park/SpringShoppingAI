# 12-6. 평가 결과로 변경을 판단하고 운영에서 관찰하기

## 이번 수업의 목표

12-1~5 이후의 선택 보충입니다. 모델·프롬프트·검색 설정을 바꿨을 때 품질 변화와 운영 비용을 구분해 비교합니다. 여기서는 평가 설계를 배우며 자동 배포 판정 시스템을 추가하지 않습니다.

## 1. 질문과 판정 기준을 먼저 고정하기

“모델 B가 더 좋다”는 판단에는 어떤 질문에서 어떤 기준으로 비교했는지가 필요합니다.

| 사례 종류 | 쇼핑 질문 예 | 확인할 결과 |
|---|---|---|
| 정상 요청 | 미개봉 상품의 반품 기간은? | 해당 조건의 근거와 답변 일치 |
| 경계 조건 | 배송비 포함 13000원으로 가능한가요? | 상품가만으로 예산 통과시키지 않음 |
| 정보 부족 | 그걸 다른 주소로 보내줘 | 대상·주소를 확인하고 임의 실행하지 않음 |
| 복합 요청 | 음료 추천과 반품 기간도 알려줘 | 두 결과 항목의 누락 여부 |
| 도구·모델 장애 | 정책 검색이 실패한 상황 | 정상 답변과 오류·보류를 구분 |

위 표는 **평가 세트 설계 예시**입니다. 현재 12장 API가 이 사례를 모두 구현했다는 뜻은 아닙니다. 기존 고정 사례는 비교 기준으로 유지하고, 실제 실패 사례를 추가하되 반복 조정에 사용하지 않을 확인용 사례도 따로 둡니다.

## 2. 한 점수로 합치기 전에 분리해서 보기

12-1의 코드 검사는 명시적인 값과 출처를 비교하고, 12-2의 모델 평가는 문장의 적절성을 판정합니다. 사람 검토는 잘못된 판정과 빠진 기준을 찾는 데 필요합니다.

| 기록 항목 | 필요한 이유 |
|---|---|
| 사례·모델·프롬프트·문서 버전 | 같은 조건의 변경 전후 비교 |
| 사례별 여러 실행 결과 | 모델의 답변·도구 선택 변동 관찰 |
| 생성·평가·통신 실패의 구분 | 연결 실패를 내용 오답이나 정답으로 숨기지 않음 |
| 도구 호출·최종 업무 결과 | 성공했다고 말한 것과 실제 조회·변경 결과 비교 |
| 시간·사용량 | 품질 개선의 운영 부담 확인 |

예를 들어 총 5건 중 1건은 API 오류, 4건 중 3건이 내용 검사를 통과했다면, 전체 기준 3/5와 응답 확보 기준 3/4는 다른 값입니다. 분모와 오류 수를 함께 표시해야 비교를 해석할 수 있습니다. 이 숫자는 설명용입니다.

[Anthropic의 Agent 평가 글](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)은 반복 실행·복수 판정 기준·실제 결과를 구분합니다. 이번 교재는 그 관점을 참고하며 해당 회사의 내부 평가 체계를 재현한 것은 아닙니다.

## 3. 운영에서는 어떤 측정을 연결할까?

[12-4](04-actuator.md)의 메트릭은 호출 수·시간·토큰을 관찰하는 출발점입니다. 다음은 운영 설계에서 정할 측정 범위이며 현재 실습이 모두 출력하는 항목은 아닙니다.

- 사용자 요청 전체와 그 안의 모델·검색·도구 호출을 요청 ID로 연결합니다.
- 평균 지연 외에 느린 요청이 어느 정도인지 분포도 살펴봅니다.
- 생성·평가·임베딩 사용량을 구분합니다. 재시도가 실제로 어디서 집계되는지도 확인합니다.
- 오류 종류와 보류·결과 없음 같은 업무 결과를 구분합니다.
- 질문 원문이나 사용자 ID를 무제한 메트릭 태그로 넣지 않고, 필요한 진단 정보만 접근을 제한해 기록합니다.

Micrometer 측정을 Prometheus 같은 장기 보관 시스템에 연결할 수 있습니다. [Canonical의 Spring AI 관측 튜토리얼](https://ubuntu.com/developers/docs/tutorials/java-advanced/spring-ai/springai-observability/)은 그 연결의 공개 예제입니다. 이 저장소의 기본 Actuator 실습에는 Prometheus 서버나 대시보드를 추가하지 않습니다.

## 확인 질문

1. 5건 중 1건이 API 오류이고 3건이 정답이면 “정확도 75%”만 출력해도 비교가 충분한가요?
2. 평가 모델이 통과시킨 답변은 사람 검토 대상에서 모두 제외해도 되나요?
3. 평균 응답 시간만으로 일부 사용자의 긴 대기를 파악할 수 있나요?

<summary>해설</summary>

1. 부족합니다. 응답이 있는 4건 기준 3/4인지 전체 5건 기준 3/5인지와 오류 1건을 함께 밝혀야 합니다.
2. 아닙니다. 모델 평가도 오판할 수 있습니다. 반례·중요 업무·표본을 사람이 검토해 판정 기준을 점검합니다.
3. 어렵습니다. 평균이 같아도 일부 요청만 매우 느릴 수 있습니다. 지연 분포와 단계별 시간을 함께 봅니다.
