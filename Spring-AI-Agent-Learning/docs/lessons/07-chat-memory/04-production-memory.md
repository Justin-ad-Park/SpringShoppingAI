# 07-4. 상용 서비스의 대화 저장과 재사용

## 이번 수업의 목표

[07-1~3](../07-chat-memory.md)의 기본 실습을 마친 뒤 읽는 선택 보충입니다. 최근 문맥과 전체 이력·업무 상태를 구분하고, 영구 저장소를 연결할 때 바뀌는 책임을 설명합니다. Advisor 연결은 [08장](../08-advisors.md)을 배운 뒤 다시 읽어도 됩니다.

이 문서는 **공개 튜토리얼·공급사의 연동 가이드와 Spring AI 2.0.2 소스를 바탕으로 정리한 설계 예시**입니다. 특정 쇼핑몰의 실제 운영 구성을 확인한 사례 보고서는 아닙니다. 저장소 연결의 실행 예제는 07-1의 테스트 패키지에 있으며, 이 문서는 운영 설계를 다룹니다. 기본 채팅 실습은 계속 메모리 저장을 사용합니다.

## 1. 대화 데이터를 세 가지 용도로 구분하기

고객이 “예산은 3만 원이야”라고 말하고 여러 차례 질문한 뒤 “아까 예산으로 골라줘”라고 했다고 가정합니다.

| 보관할 정보 | 필요한 이유 | 쇼핑 서비스의 예 |
|---|---|---|
| 전체 대화 이력 | 채팅 화면 재조회·상담 이력 확인 | 처음부터 주고받은 질문과 답변 |
| 모델에 다시 보낼 문맥 | 다음 질문 해석 | 최근 대화 메시지와 필요한 요약 |
| 업무 상태 | 정확한 조건 유지·업무 처리 | 현재 예산 30000원, 선택한 카테고리 |

최근 메시지 6개에 예산 언급이 없다면 메시지 창만으로는 처음 예산을 복원할 수 없습니다. 계속 유지할 조건은 별도 업무 상태로 관리하고, 다음 요청을 만들 때 최근 대화와 함께 전달하는 설계를 고려합니다. 주문 금액이나 재고처럼 바뀌는 사실은 대화 속 예전 답변을 재사용하기보다 업무 API로 다시 조회합니다.

이 구분은 세 종류의 DB를 반드시 만들라는 뜻이 아닙니다. 같은 DB를 사용해도 보존 기간·수정 방식·조회 목적을 구분해야 한다는 뜻입니다. Spring AI의 `ChatMemory`는 전체 이력 보관을 대신하지 않습니다. [Oracle의 Chat Memory 연동 안내](https://docs.oracle.com/en/database/oracle/oracle-database/26/aintg/spring-ai-integration-guide/chat-memory.html)도 두 용도를 구분합니다.

## 2. 한 번의 채팅에 저장한 정보를 활용하는 순서

다음은 **상용 쇼핑 상담을 위한 설계 예시**이며 현재 실습의 추가 구현은 아닙니다.

1. 로그인한 사용자가 해당 대화의 소유자인지 확인합니다.
2. 새 질문에 요청 ID를 부여해 재전송 여부를 구분합니다.
3. 같은 대화의 최근 메시지와 유지할 상담 조건을 조회합니다.
4. system 지침 + 상담 조건 + 최근 메시지 + 새 질문으로 모델 입력을 만듭니다.
5. 필요한 상품·주문·정책 정보는 도구나 검색으로 조회합니다.
6. 결과를 검증한 뒤 전체 이력·대화 메모리·상담 조건을 각 정책에 맞춰 갱신합니다.
7. 답변과 처리 상태를 화면에 반환합니다.

모델 호출 실패를 이력에 남길 수도 있지만, 실패한 질문을 다음 문맥에 포함할지는 별도 결정입니다. 전체 이력에는 실패 상태를 보관하면서 모델 문맥에는 완료된 대화만 넣는 식으로 설계할 수 있습니다. 스트리밍 응답을 중간에 취소했다면 일부 출력과 완료된 답변도 구분합니다.

화면용 `GET /conversations/{id}/messages`와 모델용 `ChatMemory.get(id)`는 조회 목적이 다릅니다. 모델이 보낸 답변에 “기억한다”는 표현이 있는지보다 **실제 요청 메시지에 필요한 정보가 포함됐는지**로 재사용 여부를 검사합니다.

## 3. 저장소 연결과 운영 설계의 연결

구현체 생성과 Spring 빈 연결 코드는 [07-1의 JDBC 자동 구성](01-messages.md#jdbc-자동-구성-db-저장소를-어디서-받을까)과 [InMemory·Redis 선택](01-messages.md#inmemory와-redis를-함께-구성하고-실행-중-선택하기)으로 옮겼습니다. 기본 저장소 생성 → 자동 구성 → 여러 저장소 선택 순서로 읽고 실행합니다.

외부 DB에 메시지를 보관해도 현재 실습의 저장 키는 HTTP 세션 ID를 사용합니다. 서버 재시작으로 세션이 사라지면 같은 키를 다시 찾지 못할 수 있으므로, **저장소 도입과 안정적인 사용자·대화 ID 설계를 함께** 해야 합니다. 여러 저장소를 선택할 때도 같은 대화가 어느 저장소에 있는지 서버에서 유지해야 합니다.

## 4. DB 저장만으로 해결되지 않는 운영 문제

| 문제 | 왜 생길까? | 설계할 기준 |
|---|---|---|
| 다른 사용자의 대화 조회 | 대화 ID를 안다는 것과 권한이 있다는 것은 다름 | 조회·전송·삭제 전에 소유권 검사 |
| 같은 대화에 동시 질문 | 두 요청이 같은 이전 목록을 읽고 각각 저장 가능 | 대화별 순서 보장, 버전 검사·재시도 등 정책 선택 |
| 재전송으로 메시지 중복 | 네트워크 오류 뒤 같은 질문이 다시 도착 | 요청 ID와 중복 처리 기준 |
| 여러 서버의 상태 불일치 | 프로세스 내부 메모리·잠금은 다른 서버와 공유 안 됨 | 공용 저장소와 서버 간 동시성 정책 |
| 오래된 대화가 계속 누적 | 메시지 개수 제한이 대화 개수·보관 기간 제한은 아님 | 보존 기간, 만료 정리, 사용자별 한도 |
| 개인정보의 불필요한 재전송 | 저장 원문을 그대로 모델에 다시 보냄 | 저장·외부 전송 항목 최소화와 마스킹 |

현재 서비스의 `synchronized`는 한 인스턴스에서 모든 메모리 요청을 직렬 처리합니다. 다른 서버까지 보호하지 않으며, 공용 DB 자체가 조회 → 모델 호출 → 저장 전체를 한 작업으로 묶어 주지도 않습니다. 모델 응답을 기다리는 동안 DB 트랜잭션을 길게 유지하는 방식보다 대화별 처리 순서와 충돌 정책을 먼저 설계합니다.

`ChatMemory.clear(id)`는 그 메모리 저장소의 해당 대화를 지웁니다. 별도 전체 이력·요약·사용자 상태가 있다면 사용자가 요청한 삭제 범위에 맞게 함께 처리해야 합니다. 세션 만료가 메모리 자동 삭제를 의미하지도 않습니다.

## 5. 대화가 길어지면 무엇을 바꿀까?

| 방식 | 얻는 점 | 잃거나 추가로 검증할 점 |
|---|---|---|
| 최근 메시지 창 | 구현과 관찰이 단순 | 오래된 조건이 사라짐 |
| 이전 대화 요약 + 최근 메시지 | 초기 문맥을 짧게 이어 갈 수 있음 | 요약 호출 비용·지연과 내용 누락·왜곡 |
| 명시적인 상담 상태 | 예산·선택 상품 등 필요한 조건 유지 | 사용자 변경·취소 시 갱신 규칙 |
| 관련 과거 내용 검색 | 긴 이력에서 필요한 일부를 선택 | 검색 누락·오래된 정보와 현재 조건 충돌 |

Dan Vega의 [Compacting Chat Memory Advisor 예제](https://github.com/danvega/compacting-chat-memory-advisor)는 오래된 대화를 요약하는 확장을 보여 줍니다. **`MessageWindowChatMemory` 자체의 자동 요약 기능이 아닙니다.** 08장 이후 선택 심화로 읽고, 기본 수업에서는 먼저 창 밖으로 사라지는 정보를 관찰합니다.

도구 호출까지 포함하는 Agent라면 저장할 메시지 종류도 확인해야 합니다. 2.0.2의 JDBC 저장소는 도구 호출을 담은 assistant 메시지와 도구 응답 메시지를 저장하지 않는 제약이 있습니다. 텍스트 대화의 영구 저장과 도구 실행 전체의 감사 기록은 같은 보장이 아닙니다. 실제 연동 전에 사용 버전의 소스와 [공식 제한 사항](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)을 확인합니다.

## 확인 질문

1. 메시지 창을 JDBC에 저장하면 채팅 화면의 전체 이력도 보존되나요?
2. 서버가 두 대라면 `synchronized`와 공용 DB만으로 같은 대화의 처리 순서가 보장되나요?
3. DB에서 예전 대화를 복구했는데도 사용자가 대화를 이어 가지 못한다면 어떤 식별값을 확인해야 하나요?
4. 긴 대화를 요약하면 항상 원래 조건을 정확히 유지할 수 있나요?

<details>

1. 아닙니다. 창 정책으로 제거한 메시지는 그 저장소의 현재 목록에서 사라집니다. 전체 이력이 필요하면 별도로 보관합니다.
2. 아닙니다. 잠금은 해당 인스턴스에만 적용됩니다. 공용 DB를 사용해도 두 요청이 같은 이전 목록을 읽을 수 있으므로 대화별 동시 갱신 정책이 필요합니다.
3. 사용자 ID·대화 ID와 저장 키의 구성입니다. 임시 세션 ID가 달라졌다면 이전 키에 접근하지 못할 수 있습니다. 복구 후에도 소유권 검사를 해야 합니다.
4. 아닙니다. 요약도 모델의 결과이므로 누락·왜곡될 수 있습니다. 중요한 조건은 구조화된 상태와 원문으로 대조하고, 요약의 비용과 지연도 측정합니다.
