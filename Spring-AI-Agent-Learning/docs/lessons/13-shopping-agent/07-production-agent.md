# 13-7. 상담 예제를 상용 기능으로 확장할 때의 경계

## 이번 수업의 목표

13-1~4 이후의 선택 보충입니다. 현재 상담 예제의 보장 범위와 추가 요구사항을 구분합니다. 아래는 쇼핑 서비스의 **설계 제안**이며 주문·결제나 새 Agent 프레임워크를 구현한 실습은 아닙니다.

## 1. 현재 샘플이 확인하는 것부터 출발하기

| 책임 | 현재 예제 | 추가 요구가 생겼을 때 |
|---|---|---|
| 조건 해석 | 이전 대화와 새 질문에서 업무·예산·카테고리 추출 | 모호한 조건·복합 의도·상충 조건 평가 |
| 조회 | 허용 도구를 제공하고 실행 결과 기록 | 로그인 권한·실제 업무 API 연결 |
| 검증 | 조회한 ID·총액·카테고리·출처 검사 | 요청 항목 전체의 충족 여부 확인 |
| 대화 저장 | 정상·결과 없음·실패별 저장 시점 구분 | 영구 이력·명시적 상담 상태·만료 정책 |
| 실행 제한 | 모델 요청·도구 실행·전체 시간의 범위별 제한 | 동시 사용자·원격 실패·운영 용량 기준 |

예제의 `VERIFIED`는 현재 검사 범위의 통과를 나타냅니다. 상품 추천과 반품 안내를 함께 요청했는데 상품만 답했다면, ID·금액이 맞아도 요청 전체를 충족하지 못했을 수 있습니다. 이 한계는 [13-3](03-verify.md)에 명시돼 있습니다.

## 2. 복합 요청에서 빠진 결과를 확인하기

“음료를 추천하고 반품 기간도 알려줘”에는 상품 추천과 정책 안내라는 두 요구가 있습니다. 운영 설계에서는 필요한 결과 항목을 먼저 기록하고, 각 항목에 실제 근거가 있는지 검사할 수 있습니다.

| 필요한 결과 | 완료 근거의 예 | 없을 때의 선택 |
|---|---|---|
| 상품 추천 | 현재 상품·배송비 조회와 예산 검사 | 확인된 결과 없음 또는 재질문 |
| 반품 안내 | 해당 조건의 정책 검색과 원문 대조 | 정책 답변 보류 |

정책 검색이 실패했을 때 “추천만 우선 제공하고 정책은 보류”할지, 전체 응답을 보류할지는 제품 정책입니다. 빈 목록만 보고 완료로 판단하지 않고, 조회 실패와 실제 결과 없음을 구분합니다. 이 표의 확장 검증은 기본 샘플에 구현돼 있지 않습니다.

## 3. 조회와 주문 실행을 분리하기

현재 예제는 조회·추천입니다. “이 상품으로 주문해줘”를 확장하면 모델이 선택한 상품과 실제 주문 가능 상태 사이에 추가 검사가 필요합니다.

1. 서버가 로그인 사용자와 구매 권한을 확인합니다.
2. 가격·재고·배송지를 업무 API로 다시 확인합니다.
3. 최종 조건과 사용자 확인 범위를 확정합니다.
4. 요청 ID로 중복 주문을 방지하며 업무 서비스를 호출합니다.
5. 주문 시스템의 처리 결과를 확인한 뒤 완료를 표시합니다.

모델의 “주문 완료” 문장은 업무 시스템의 주문 생성 결과를 대신하지 않습니다. 시간 초과 이후에도 이미 수행된 주문이 있을 수 있으므로 결과 조회·중복 방지 설계를 해야 합니다. 원격 도구에서는 [11-7](../11-mcp-workflow-agent/07-production-mcp.md)의 기준을 함께 봅니다.

## 4. 복잡해지기 전에 무엇을 평가할까?

조건 추출·도구 선택·결과 검증·저장은 독립적으로 개선할 수 있는 경계입니다. 먼저 어디서 실패하는지 사례와 실행 기록으로 확인하고, 그 문제에 필요한 책임만 분리합니다. 단순히 클래스나 Agent 수를 늘리는 것이 개선은 아닙니다.

- 후속 요청에서 변경하지 않은 조건을 유지하는가?
- 정책만 물었을 때 불필요한 상품 작업을 하지 않는가?
- 복합 요청의 일부 누락을 탐지하는가?
- 도구 실패·시간 초과 뒤 잘못된 완료 상태나 대화가 남지 않는가?
- 문서·모델 변경 뒤 품질과 비용이 어떻게 달라지는가?

실제 모델 평가에는 한 번의 정상 예제 외에 반복·반례가 필요합니다. [12-6](../12-evaluation/06-production-evaluation.md)의 평가 설계를 사용하고, 의도 분류만 비교할 때는 기존 [13-5](05-intent-classification.md)·[13-6](06-intent-quality-evaluation.md)을 읽습니다. 영구 대화 저장은 [07-5](../07-chat-memory/05-production-memory.md)로 연결합니다.

## 확인 질문

1. 유효한 상품을 추천했다면 함께 요청한 정책 안내까지 완료됐다고 봐도 되나요?
2. 대화 메모리에 남은 상품 가격으로 주문 금액을 확정해도 되나요?
3. 실패가 늘었을 때 여러 Agent로 나누는 작업부터 시작해야 하나요?

<details>
<summary>해설</summary>

1. 아닙니다. 복합 요청의 필요한 결과를 나누어 확인해야 합니다. 현재 기본 검증은 일부 누락까지 확인하지 않습니다.
2. 안 됩니다. 가격·재고는 변할 수 있습니다. 주문 직전에 업무 시스템에서 확인한 사실로 처리해야 합니다.
3. 아닙니다. 먼저 어떤 단계·조건에서 실패하는지 평가합니다. 확인된 문제를 해결하는 최소 변경부터 적용합니다.

</details>
