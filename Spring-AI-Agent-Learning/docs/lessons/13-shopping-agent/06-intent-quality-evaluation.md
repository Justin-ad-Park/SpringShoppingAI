# 13-6. 같은 질문으로 의도 분류 모델 비교하기

**실행 코드·질문 세트:** [labs/13-06-intent-quality-evaluation](../../../labs/13-06-intent-quality-evaluation/README.md).

**이번 목표:** 같은 분류표와 최대 5개 문의를 저비용 OpenAI 모델에 보내고, 기대한 판단·대분류·소분류와 일치하는지 비교합니다. 질문과 정답을 추가해 작은 평가 세트를 확장하는 방법도 확인합니다.

**선수 수업:** [13-5 계층형 의도 분류](05-intent-classification.md). 이 수업은 13-5의 분류표·프롬프트·서비스를 그대로 재사용합니다.

## 1. 모델 품질은 같은 문제를 풀게 한 뒤 비교합니다

모델 이름이나 가격만으로 우리 문의를 얼마나 잘 분류할지 알 수 없습니다. 비교하려면 모든 모델에 같은 질문, 같은 지시문, 같은 분류표를 전달해야 합니다. 기대 결과를 미리 정해 두면 각 결과를 그 기준과 비교할 수 있습니다.

이 실습은 OpenAI API에서 사용할 수 있는 비용이 낮은 모델 세 가지를 선택했습니다. 모델 접근 권한과 가격은 바뀔 수 있으므로 실행 전 [공식 모델 문서](../../references.md)에서 확인합니다. 표의 가격은 2026-11-10 확인 기준, 표준 입력/출력 토큰 백만 개당 USD입니다. 시험 요청의 실제 사용량·비용은 별도 API 사용량에서 확인해야 합니다.

| 모델 ID | 공식 설명의 용도 | 입력 / 출력 가격 |
|---|---|---:|
| `gpt-6-luna` | 비용 민감·대량 작업 | $0.10 / $0.50 |
| `gpt-5.6-luna` | 비용 민감·대량 작업 | $0.20 / $1.20 |
| `gpt-5.4-mini` | 빠르고 효율적인 mini 모델 | $0.75 / $4.50 |

모델의 세대와 가격만으로 분류 성능의 순위를 미리 정하지 않습니다. 평가 결과는 실행 날짜, 프롬프트, 분류표, 질문 세트와 함께 읽어야 비교할 수 있습니다.

## 2. 다섯 개 질문으로 무엇을 확인하나요?

[질문 파일](../../../labs/13-06-intent-quality-evaluation/src/test/resources/intent-evaluation-cases.json)에 문의와 기대 판단을 함께 적습니다. 현재는 환불 시점, 반품 접수 철회, 발송 전 주문 취소, 복수 요청, 수령 후 반품 접수를 포함합니다.

| 질문의 목적 | 문의 일부 | 기대 결과 |
|---|---|---|
| 환불과 반품 구분 | 반품은 완료됐고 환불금이 언제 입금되는지 | `REFUND:TIMING` |
| 비슷한 단어의 업무 구분 | 접수한 반품 신청을 취소 | `RETURN:WITHDRAW` |
| 주문 처리 | 발송 전 주문을 취소 | `ORDER:CANCEL` |
| 복수 요청 보류 | 주문 취소와 포인트 잔액 조회 | `MULTIPLE` |
| 수령 후 취소 표현 | 상품을 받은 뒤 “주문 취소”라고 말하며 반품 접수 가능 여부를 질문 | `RETURN:REQUEST` |

반품 철회 질문에는 “이미 접수한 반품 요청을 되돌린다”는 설명을 넣었습니다. 또 상품을 이미 받은 뒤 “주문 취소”라고 표현한 문항으로 `ORDER:CANCEL`과 `RETURN:REQUEST`의 경계를 확인합니다. 단어만 좇으면 `ORDER:CANCEL`에 끌릴 수 있고, 상품을 받은 뒤 반품 접수를 묻는 문맥까지 읽으면 `RETURN:REQUEST`를 골라야 합니다. 이 사례가 하위 모델에서 실제로 더 어렵게 작동하는지는 Live 결과로 확인해야 합니다.

2026-11-10 Live 실행에서는 수령 후 반품 접수 문항을 `gpt-6-luna`와 `gpt-5.6-luna`가 맞혔고, `gpt-5.4-mini`는 `CLARIFY`로 보류했습니다. 같은 실행에서 반품 신청 철회 문항도 모델별 결과가 달랐습니다. 이는 다섯 문항의 한 번의 관찰 결과이며, 작은 모델이 항상 이 문항을 틀린다거나 모델 간 일반 성능 순위를 뜻하지 않습니다.

이 평가의 [의도 분류 JSON](../../../labs/13-05-intent-classification/src/main/resources/intent-catalog.json)과 질문은 모델별 분류 차이와 실패가 드러나도록 만든 교육용 자료입니다. 분류표의 `description`은 프롬프트에 함께 전달되므로, 의미와 포함·제외 기준을 더 구체적으로 쓰면 분류 정확도를 높일 수 있습니다. 예를 들어 `RETURN:REQUEST` 설명에 “상품을 받은 뒤 새 반품을 접수하거나 접수 가능 여부를 묻는 경우”를 명시하고, `ORDER:CANCEL` 설명에는 “발송 전 주문 취소”를 명시하면 두 업무의 경계가 분명해집니다. 질문 세트와 모델을 그대로 둔 채 설명만 바꿔 다시 평가하면 설명 수정의 효과를 비교할 수 있습니다. 다만 설명을 보완해도 모든 모델의 정확도가 반드시 높아지는 것은 아니므로, 실제 결과로 확인해야 합니다.

문의와 기대 답을 추가하려면 JSON 배열에 항목을 넣습니다. 현재 최대 5개 제한은 한 번의 Live 실행에서 발생할 수 있는 API 호출·비용을 작게 유지하기 위한 교육용 범위입니다. 질문 수를 늘리면 모델마다 같은 수만큼 요청이 늘어납니다.

## 3. 평가는 답을 미리 정해 놓은 기준과 비교합니다

이 실습의 정답 기준은 별도 평가 모델의 의견이 아니라 질문 파일에 적은 `expected_decision`, `expected_main_intent`, `expected_sub_intent`입니다. 각 모델의 결과가 세 필드와 모두 일치하면 정답 1건으로 셉니다. `MULTIPLE`이나 `OUT_OF_SCOPE`는 두 의도 코드가 모두 없는 경우에만 정답입니다.

**정답 일치율**은 정답과 일치한 문항 수를 전체 문항 수로 나눈 값입니다. 예를 들어 5개 중 4개가 맞으면 이 질문 세트의 일치율은 80%입니다. 응답이 깨졌거나 호출에 실패한 경우는 오류로 표시하고 정답으로 세지 않습니다.

다섯 문항은 모델의 전체 한국어 이해력이나 상용 서비스 정확도를 나타내지 않습니다. 실제 적용에는 업무 로그에서 대표 질문을 모으고, 사람의 검토를 거친 정답을 만들며, 훨씬 큰 평가 세트로 반복 검증해야 합니다. 질문 하나의 표현만 바뀌어도 결과가 달라질 수 있습니다.

## 4. Spring AI에서 요청 모델을 바꿉니다

테스트는 앞 실습의 `IntentClassificationService`를 사용합니다. 분류표와 프롬프트를 복제하지 않고 Gradle 프로젝트 의존성으로 재사용합니다. `ChatClient.Builder.clone()`으로 기존 연결 설정을 복사한 다음, `OpenAiChatOptions`에서 모델 ID만 지정해 새 분류기를 만듭니다.

```java
var classifier = new IntentClassificationService(
        chatClientBuilder.clone()
                .defaultOptions(OpenAiChatOptions.builder().model(model)),
        intentCatalog,
        objectMapper);
```

따라서 세 모델은 동일한 분류 지시문과 업무 목록을 받습니다. 테스트는 각 모델에 같은 문의를 순서대로 보내고 결과를 모아 모델별 정답 수·비율·문항별 출력을 표시합니다. 실패 응답은 오류로 남기고 다음 질문을 평가합니다.

## 5. Live 실습 실행과 결과 읽기

이 테스트는 고정 응답을 쓰지 않으며 실행할 때 실제 OpenAI API를 모델마다 호출합니다. 설정한 모델 ID를 계정에서 사용할 수 있어야 하고 사용량 비용이 발생합니다.

```bash
./gradlew :Spring-AI-Agent-Learning:labs:13-06-intent-quality-evaluation:test --tests '*IntentModelQualityOpenAiLiveTest' --console=plain
```

출력의 `정확도`는 이번 다섯 질문의 정답 일치 비율입니다. 한 문항의 오답과 오류를 함께 읽어 어떤 경계에서 차이가 났는지 봅니다. 모델 비교 결과는 이 질문 세트·실행 시점에 한정됩니다.

기존 13-5에는 환불 시점 문의를 추가한 별도 OpenAI Live 사례가 있습니다. 모델별 비교는 기본 분류 구현과 코드가 섞이지 않도록 이 소주제 모듈에 둡니다.

## 확인 질문

1. 세 모델의 분류 결과를 공정하게 비교하려면 무엇을 같게 유지해야 하나요?
2. 이 실습에서 정답 일치율은 어떤 기준으로 계산하나요?
3. 다섯 질문에서 100%를 받은 모델을 상용 전체 문의에 가장 정확한 모델이라고 말할 수 있나요?
4. 반품 철회와 주문 취소 질문은 어떤 분류 차이를 확인하나요?

<details>
<summary>해설</summary>

1. 모델에 전달하는 문의, 분류표, 프롬프트와 기대 정답을 같게 유지합니다. 이 실습은 모델 ID만 바꿉니다.
2. 기대한 판단과 대분류·소분류가 모두 일치한 수를 전체 질문 수로 나눕니다. 보류 판단은 두 코드가 모두 비어 있어야 일치합니다.
3. 아닙니다. 다섯 개 교육용 질문에 대한 결과일 뿐입니다. 실제 문의를 대표하는 더 큰 평가 세트와 사람의 정답 검토가 필요합니다.
4. 둘 다 “취소”라는 표현이 있지만 기존 반품 접수 철회는 `RETURN:WITHDRAW`, 발송 전 주문 취소는 `ORDER:CANCEL`로 나뉩니다.

</details>
