# 교육 계획

## 대상과 목표

선수 지식은 Java 클래스·생성자, Spring DI, 간단한 REST Controller와 Service입니다.
Java record, Reactor, Vector DB, LLM API, Agent 프레임워크 경험은 가정하지 않습니다.
필요한 개념은 해당 수업에서 먼저 설명합니다.

최종 결과물은 가상 상품 검색, 배송비 조회, 반품 규정 검색, 후속 질문을 처리하는 쇼핑 상담 Agent입니다.
금액 계산과 권한 검사는 Java 코드가 담당하고, 모델이 맡는 판단 범위를 설명할 수 있어야 합니다.

## 교재 작성 원칙

1. 한 수업에 주요 새 개념 하나를 도입합니다. 새 용어는 코드보다 먼저 정의합니다.
2. 문제 → 익숙한 Spring 구조 → 새 개념 → 전체 최소 코드 → 실행 → 결과 해석 순으로 설명합니다.
3. 코드에는 import·설정·실행 위치를 포함합니다. 처음부터 프런트엔드나 공통 추상화는 추가하지 않습니다.
4. 정상 동작 뒤에 코드/입력 하나만 바꾸는 실험과 실패 사례를 둡니다.
5. 문장 암기 대신 “누가 결정하고 어디서 실행하는가?”를 설명하게 합니다.
6. 가짜 모델 테스트, 실제 모델 실험, 아직 구현하지 않은 기능을 명시합니다.
7. 외부 자료는 보충 읽기입니다. 한국어 교재만으로 기본 실습을 따라갈 수 있게 합니다.

## 한 단원을 작은 수업으로 읽기

[학습 방법](learning-guide.md)을 기준으로 각 단원의 목차에서 소수업에 들어갑니다.
04~12는 기존 구현을 29개 설명 수업으로 나눴습니다. 번호와 실행 모듈은 유지하므로 기존 링크·실습 명령을 계속 사용할 수 있습니다.
한 소수업은 30~45분을 기준으로 하며, 아래 시간은 단원 전체의 기존 추정치입니다.
보충 읽기는 기본 메서드를 이해한 뒤 선택합니다. 특히 06의 실행 상한 내부 구현은 Workflow/Agent 기본 비교와 분리했습니다.

## Workflow와 Agent 비교 수업

선수 조건: 04의 조건 객체와 05의 `searchProducts`, `calculateShipping` 도구를 이해한 상태.
이 수업에서는 새 도메인·새 외부 API·새 UI를 추가하지 않습니다.

### 비교 요청

“배송비까지 합쳐 3만원 이하인 선물을 추천해줘.”

| 구분 | Workflow 버전 | Agent 버전 |
|---|---|---|
| 흐름 결정 | Java 코드가 추출 → 검색 → 배송비 → 답변 순서 지정 | 모델이 목표와 도구 결과를 보고 다음 도구 선택 |
| 모델 역할 | 단계별 추출·요약 | 도구 선택·인자 생성·추가 조회 여부 판단 |
| 프롬프트 | 현재 단계의 작업과 출력 형식 | 목표·제약·도구 사용 기준·종료 기준 |
| 실행 | 코드가 서비스를 직접 호출 | 모델이 요청하고 Spring AI/애플리케이션이 도구 실행 |
| 보장 | 정의한 제어 흐름을 코드로 강제 | 호출 횟수·시간·허용 도구를 애플리케이션에서 제한 |

Workflow도 분기와 모델 분류를 포함할 수 있습니다. Agent도 제약을 따릅니다.
분류 기준은 “프롬프트에 Agent라는 단어가 있는가”가 아니라 **다음 행동을 누가 결정하는가**입니다.

### 프롬프트 비교

Workflow의 조건 추출 프롬프트:

```text
사용자 요청에서 상품 카테고리와 최대 총예산을 추출하라.
정해진 JSON 구조로 반환하고, 누락된 값은 null로 표현하라.
```

이후 검색과 배송비 조회는 Java 코드가 실행합니다.

Agent의 프롬프트:

```text
배송비를 포함한 예산에 맞는 선물을 추천하라.
필요한 경우 상품 검색과 배송비 조회 도구를 사용하라.
확인하지 않은 가격과 배송비를 만들지 마라.
필수 정보가 부족하면 사용자에게 질문하라.
추천 가능한 상품을 확인했거나 더 진행할 수 없으면 이유와 함께 답하라.
```

순서를 프롬프트에 적는 것은 모델에 대한 지시입니다. 순서를 반드시 보장하려면 코드로 강제해야 합니다.
보안·금액·변경 승인 규칙은 프롬프트만으로 보장하지 않습니다.

### 3시간 구성과 관찰 항목

1. 30분: 기존 도구 복습, 두 구조의 호출 흐름 손으로 그리기.
2. 45분: Workflow 구현. 조건 추출 이후는 Java 호출로 연결.
3. 45분: 같은 도구를 Agent에 제공. 도구 이름·인자·결과·호출 횟수 기록.
4. 30분: 검색 결과 없음, 예산 누락, 예산 초과, “상품 이름만 알려줘” 입력 비교.
5. 30분: 혼합 구조 구성과 설명. 조회 선택은 모델, 가격 검증·실행 제한은 코드.

기록은 관찰 가능한 도구 호출과 결과를 사용합니다. 모델의 내부 사고 과정을 요구하지 않습니다.
요청별 최상위 `ChatClient` 호출 수와 내부 도구 호출 수를 따로 셉니다.
최대 도구 호출 수 초과와 총 실행 시간 초과를 실제로 유도하고 종료·오류 응답을 확인합니다.
숫자 제한은 Java 설정/코드로 강제하고, 프롬프트에 적은 제한과 비교합니다.

완료 질문:

- 이 단계의 순서를 바꾸려면 Java 코드와 프롬프트 중 무엇을 바꿔야 하는가?
- 모델이 아무 도구도 선택하지 않을 수 있는가? 그 결과를 어떻게 확인했는가?
- 도구 결과가 예산을 넘으면 누가 계산하고 누가 재검색 여부를 결정하는가?
- Workflow 안의 모델 분류와 Agent의 다음 행동 선택은 무엇이 다른가?

## 구현 범위와 선택 심화

04~12는 각각 독립 실행 가능한 모듈로 구현했습니다. 07은 이전 메시지를 직접 조립하며 아직 Advisor를 사용하지 않습니다.
08 Advisor → 09 임베딩과 검색 → 10 RAG → 11 평가 → 12 통합 순서로 확장합니다.
단원마다 구현·테스트·커밋을 마친 뒤 다음으로 넘어갔습니다.
그림은 [다이어그램 공통 기준](diagram-guide.md)을 적용하고, 앞으로 배울 코드에 의존하지 않습니다.

MCP는 로컬 도구를 원격 도구로 교체하는 선택 수업으로 둡니다.
멀티 에이전트·Skills·A2A, 외부 Vector DB, 스트리밍 UI, 이미지/음성은 필수 과정 이후로 미룹니다.
RAG나 MCP가 있어야만 Agent를 만들 수 있는 것은 아닙니다.
